## 一、开场：整车网络的三条腿 + 拓扑图

### 1.1 一个贯穿全文的类比——"会议室里按优先级发言"

CAN 总线像一间会议室：所有人（ECU）共享同一根麦克风线，**谁想说话都要先听有没有人在讲**；如果同时有两个人开口，**ID 小的（优先级高）继续讲，ID 大的立刻闭嘴重听**。这就是"非破坏性仲裁（arbitration）"——总线永远被最高优先级的那条报文占据，且不会冲突损坏。

```
会议室规则（CAN 仲裁）                CAN 真实机制
─────────────────────────────────────────────────────
两人同时起立发言 → 比工牌号        两 ECU 同时发帧 → 比 ID（越小优先级越高）
工牌小的继续、大的退下重听           ID 大的退出发送、ID 小的继续，不破坏帧
只有一根麦克风线                    一条差分双绞线（CAN_H / CAN_L）
```

LIN 则是"一个主教官带一群小兵"：单主多从，主节点定时点名，从节点才答（低速、便宜、用于车窗雨刷这类不急的件）。

车载以太网是"换成了千兆交换机的高带宽数据网"：用于 ADAS、影音、诊断大数据这类 CAN 扛不住的流量。

### 1.2 典型车机网络拓扑图（怎么读）

```
                    ┌─────────────────────────────────────────┐
                    │            整车网络（网关 Gateway）         │
   ┌───────────────┤  把动力/车身/娱乐等子网隔离并做协议路由      │
   │               └─────────────────────────────────────────┘
   │                        │                │               │
 ┌─▼─┐ 动力 CAN         ┌─▼─┐ 车身 CAN    ┌─▼─┐ 娱乐/信息 CAN  ┌─▼─┐ 以太网
 │ECU│ (引擎/制动/ABS)  │BCM│(门窗/灯光)  │车机│ (IVI/座舱)     │ADAS│(摄像头/雷达)
 │…  │                 │…  │             │SoC │←SocketCAN→MCU  │…  │←SOME/IP→
 └───┘                 └───┘             └─┬─┘                └────┘
                                            │
                                     ┌──────▼──────┐
                                     │ VHAL/原生服务 │ ← 把 CAN/LIN/以太网信号
                                     │ (vendor 层)   │    抽象成车辆属性
                                     └──────┬──────┘
                                            │ AIDL
                                     ┌──────▼──────┐
                                     │ CarService    │
                                     │ → App/系统应用 │
                                     └──────────────┘
```

> 怎么读：左边三根是**不同速率/重要性的 CAN 子网**，中间是**网关（Gateway）**做隔离与路由，车机通常只接其中几条（见第 12 章）；最右边以太网接高带宽节点。车机 SoC 通过 MCU/控制器收到 CAN 帧，再经 vendor 服务上送 VHAL → CarService → App（第 8 章详细展开）。

### 1.3 三条总线的分工速查

| 总线 | 速率 | 成本 | 典型负载 | 关键词 |
|---|---|---|---|---|
| **CAN / CAN FD** | 125K~1M（FD 到 5~8M） | 中 | 控制指令、状态 | 差分、仲裁、广播 |
| **LIN** | 1K~20K | 低 | 车窗、座椅、雨刷 | 单主多从、调度表 |
| **车载以太网** | 100M~1G（T1） | 高 | 影音、ADAS、诊断大数据 | SOME/IP、交换机 |

## 二、CAN 基础：差分信号、仲裁、帧格式、CAN FD

### 2.1 为什么用差分信号

CAN 用一对线 `CAN_H` / `CAN_L` 传输**差分电压**。抗干扰强：外界噪声会同时作用在两根线上，差值不变 → 噪声被抵消。这正是它能在发动机舱这种"电气地狱"里稳定工作的原因。

```
CAN_H ──┐                         CAN_H 比 CAN_L 高 ≈ 2V → 逻辑 0（显性 dominant）
        ├── 差分接收器算 (CAN_H - CAN_L)
CAN_L ──┘                         CAN_H ≈ CAN_L        → 逻辑 1（隐性 recessive）
```

> 关键约定：**显性（dominant，0）能覆盖隐性（recessive，1）**——这正是仲裁能"ID 小的赢"的物理基础（见 2.2）。

### 2.2 总线仲裁：ID 越小优先级越高

所有节点挂在同一条线上。当两个以上节点同时想发：

```
节点A 发 ID=0x100   ████____（先发 0 显性）
节点B 发 ID=0x200   ██____██（第二位发了 1 隐性，但线上被 A 的 0 覆盖）
        ↓
节点B 检测到"我发的 1 但线上是 0" → 立刻停止发送，等下一轮
节点A 不受影响继续发完 → 总线被最高优先级报文独占
```

这就是**非破坏性仲裁**：高优先级报文畅通无阻，低优先级自动退让，**没有任何一帧被破坏**。这也是为什么实时控制（刹车信号 ID 很小）总能抢到总线。

### 2.3 帧格式（标准帧 / 扩展帧、数据帧 / 远程帧 / 错误帧）

| 类型 | 说明 |
|---|---|
| **数据帧（Data Frame）** | 最常用，携带数据 |
| **远程帧（Remote Frame）** | 请求对方发某个 ID 的数据（现代用得少） |
| **错误帧（Error Frame）** | 节点检测到错误时广播，强制总线重发 |
| **过载帧 / 帧间隔** | 流控与间隔 |

按 ID 长度分：

| 帧 | ID 位数 | 用途 |
|---|---|---|
| **标准帧（Standard，11 位）** | 11 bit（最多 0x7FF） | 传统车身/动力控制 |
| **扩展帧（Extended，29 位）** | 29 bit（最多 0x1FFFFFFF） | 复杂系统、诊断、厂商扩展 |

### 2.4 位速率与终端电阻

- **位速率（bit rate）**：常见 125K / 250K / 500K / 1M bps，车机诊断口常是 500K。
- **终端电阻（termination）**：CAN 总线两端各接一个 **120Ω** 电阻，匹配阻抗、消除信号反射。**少接一个，总线会大量错误帧**（第 11、13 章高频坑）。

### 2.5 CAN FD 的变化（Flexible Data-rate）

传统 CAN 一帧最多 8 字节。CAN FD 放宽：

| 维度 | 经典 CAN | CAN FD |
|---|---|---|
| 数据段长度 | 最多 8 字节 | 最多 64 字节 |
| 速率 | 全帧同速 | 仲裁段慢、数据段快（最高 ~8M） |
| 兼容性 | — | 物理兼容，需控制器支持 FD |

> 注意：CAN FD 帧里"仲裁段"仍用 11/29 位 ID 和经典速率做仲裁，只有数据段提速——所以**老节点仍能听到 FD 帧的仲裁部分**，向后兼容。

### 2.6 位定时与采样点（为什么两端波特率要对齐）

CAN 不是"设个 500000 就完事"，收发双方还要**位定时（bit timing）**一致：一个位时间被切成同步段、传播段、相位段 1/2，再按**采样点（sample point）**取电平。典型采样点设在 **75%~87.5%**。

```
一个位时间 ───────────────────────────────▶
 [Sync][Prop][Phase1][Phase2]   ↑采样点
   采样点不一致 → 高速时长线易采样错 → 大量错误帧
```

> 工程坑：两块节点都标称 500K，但采样点/同步跳转宽度（SJW）配置不同，在长线缆/高负载下就会偶发错误帧。车机接车厂总线时，**位定时参数要按车厂 DBC/总线规范对齐**，不能只对准标称波特率（见第 11、13 章的 `ip -s link` 错误计数）。

## 三、CAN 报文逐字段：ID / DLC / Data / CRC / ACK

### 3.1 一帧长什么样（以标准数据帧为例）

```
 SOF | ID(11) | RTR | IDE | r0 | DLC(4) | Data(0~8B) | CRC | CRCdel | ACK | ACKdel | EOF
  ↑     ↑        ↑     ↑     ↑     ↑          ↑           ↑       ↑       ↑      ↑
起始  优先级    远程  帧类型 保留  数据长度    数据       校验    分隔   确认   分隔   帧尾
```

### 3.2 各字段含义

| 字段 | 位数 | 含义 |
|---|---|---|
| **SOF** | 1 | 帧起始（显性边沿同步） |
| **ID** | 11 / 29 | **优先级 + 报文身份**（越小越高优先级，见 2.2） |
| **RTR** | 1 | 远程帧标志 |
| **IDE** | 1 | 标准(0)/扩展(1)帧 |
| **DLC** | 4 | 数据长度 0~8（FD 另有扩展 DLC 到 64） |
| **Data** | 0~64B | 实际负载 |
| **CRC** | 15(+del) | 校验，接收方比对 |
| **ACK** | 2 | 任一节点正确收到就发显性确认 |
| **EOF** | 7 | 帧结束 |

### 3.3 11 位与 29 位 ID 的用法差异

- **11 位（0x000~0x7FF）**：传统控制报文。例如动力 CAN 上 `0x0C0` 可能是某发动机状态帧（具体由车厂 DBC 定义）。
- **29 位**：用于地址空间更大的系统、诊断、或厂商私有扩展。UDS 诊断常跑在 29 位 ID 上。

> 工程现实：ID 与信号的**具体含义由车厂的 DBC 数据库文件定义**（哪个字节第几位代表什么、怎么缩放、偏移多少）。没有 DBC，原始 CAN 帧只是一串字节。**DBC 是车机对接 CAN 的"字典"**，vendor 服务里通常内置解析逻辑。

### 3.4 多播语义对软件设计的影响

CAN 是**广播总线**：一条报文所有节点都收到。这带来两个软件设计要点：

1. **没有"点对点"概念**：车机收到某 ID 帧，不代表"这是发给我的"，只是"这条消息在总线上"。软件要按 ID 过滤自己关心的。
2. **属性更新是事件驱动**：某个 ECU 周期性广播车速帧，车机 VHAL 订阅该 ID、按 DBC 解出车速 → 上报属性变化（衔接 VHAL 篇 subscribe 机制）。**采样率由发送方周期决定，不是车机主动 poll**。

```
ECU 每 10ms 广播 0x1A0(车速) ──┐
ECU 每 50ms 广播 0x2B1(转速) ──┼─▶ 总线 ─▶ 车机 CAN 驱动收全部
车机只 filter 0x1A0/0x2B1，其余丢弃 ─▶ vendor 服务解出 → VHAL 属性

## 四、上层协议：ISO-TP、UDS、OBD-II、DoIP

CAN 一帧只有 8 字节（FD 64 字节），但诊断命令、固件数据远不止这点。需要"在 CAN 之上再叠一层"来传输更长的报文。

### 4.1 ISO-TP（ISO 15765-2，传输层）

**ISO-TP（ISO Transport Protocol）** 把大于一帧的数据**分多帧传输**，并带流控：

```
单帧（SF）：数据 ≤ 7 字节，一帧搞定
多帧（MF）：首帧(FF) 声明总长度 → 连续帧(CF) 分片发送
流控帧（FC）：接收方回"你能连发几帧、间隔多久"（防止把接收方冲垮）
```

类比：CAN 帧是"一句短话"，ISO-TP 是"把一封信拆成几张便签按顺序发，对方收到说'继续，一次发三张'"。

### 4.2 UDS 诊断服务（ISO 14229，Unified Diagnostic Services）

UDS 是车厂给 ECU 发的"诊断指令集"。车机/诊断仪通过 ISO-TP 发 UDS，**要带"服务 ID（SID）+ 子功能"**：

| SID | 名称 | 作用 |
|---|---|---|
| **0x10** | Diagnostic Session Control | 切换会话（默认/扩展/编程会话） |
| **0x22** | Read Data By Identifier | 读某个数据（如 VIN、电压、故障码） |
| **0x27** | Security Access | 安全访问（Seed-Key 解锁，见 10.4） |
| **0x2E** | Write Data By Identifier | 写数据（标定、配置） |
| **0x31** | Routine Control | 启动/停止某个例程（如自检、擦写） |
| **0x3E** | Tester Present | 保活（防止会话超时退出） |
| **0x34/0x36/0x37** | Request Download / Transfer / Exit | 刷写固件三段式 |

> 车机场景：读故障码（DTC）、读 VIN、进编程会话刷 ECU，全靠这一套。写操作（0x2E/0x31）有整车安全后果（见 10.4、12.3）。

### 4.5 一个具体的 UDS 交互（十六进制示例）

读"发动机转速"的标准诊断交互大概长这样（走 ISO-TP 分帧）：

```
诊断仪 → ECU   22 0C 0A          # 0x22 读数据，DID=0x0C0A（发动机转速）
ECU  → 诊断仪   62 0C 0A 1A 2B    # 0x62 是正响应，后跟两字节转速原始值
# 转速 = (0x1A << 8 | 0x2B) = 6699 → 按 DBC 缩放（如 /4）= 1674 rpm

诊断仪 → ECU   10 03             # 0x10 进"扩展会话"
ECU  → 诊断仪   50 03 ...         # 0x50 正响应，已进入
诊断仪 → ECU   27 01             # 0x27 请求 Seed（子功能 01）
ECU  → 诊断仪   67 01 AB CD EF 12 # 0x67 返回 Seed = AB CD EF 12
诊断仪 → ECU   27 02 K1 K2 K3 K4 # 子功能 02 + 算出的 Key
ECU  → 诊断仪   67 02             # 解锁成功，此后才能写/编程
```

> 读响应首字节 = SID+0x40（如 0x22→0x62）是正响应；若返回 **0x7F <SID> <NRC>**，就是负响应，NRC（Negative Response Code）告诉你失败原因（如 0x22=条件不满足、0x35=密钥错、0x78=请等待）。排查写失败先抓 NRC（见第 13 章"写 ECU 失败"）。

### 4.6 负响应码（NRC）速查

| NRC | 含义 | 典型原因 |
|---|---|---|
| 0x11 | 服务不支持 | 该 ECU 没实现这个 SID |
| 0x12 | 子功能不支持 | SID 有，但子功能错 |
| 0x22 | 条件不满足 | 没进对会话 / 车辆状态不对 |
| 0x33 | 拒绝访问 | 未过安全解锁（Seed-Key） |
| 0x35 | 密钥无效 | Key 算错 |
| 0x78 | 请求正确，请等待 | 操作进行中（如刷写），稍后重查 |

### 4.3 OBD-II 与 PID

**OBD-II（On-Board Diagnostics）** 是标准化的车载诊断接口（就是维修店插的那个口）。它通过一组**标准 PID（Parameter ID）**暴露发动机转速、水温、车速等：

```
请求：02 01 0C  ──▶  含义：读 PID 0x0C（发动机转速）
响应：04 41 0C 1A 2B ─▶  解出转速 = (0x1A*256+0x2B)/4 rpm
```

> OBD-II 多跑在 CAN 上（ISO 15765-4），是 ISO-TP + UDS 的一个"标准化子集"。车机想读排放/转速类标准数据，从 OBD PID 入手最稳。

### 4.4 DoIP（Diagnostic over IP，ISO 13400）

当诊断数据要跑在**以太网**上（不再走 CAN），用 **DoIP**：把 UDS 报文承载到 TCP/UDP 上，经车载以太网到达目标 ECU。

```
诊断仪 → 以太网(TCP 13400) → DoIP 网关 → 路由到对应 ECU（可能再转回 CAN）
```

> DoIP 是"诊断上以太网"的桥。它和 SOME/IP（第 6 章）不一样：DoIP 专管诊断，SOME/IP 管的是"服务/方法/事件"这种应用通信。

## 五、LIN 总线：单主多从、调度表、与 CAN 分工

### 5.1 为什么还需要 LIN

CAN 虽好但贵（收发器+控制器+双绞线）。车窗、雨刷、座椅加热这类**低速、不紧急、成本低优先**的件，用更便宜的 **LIN（Local Interconnect Network）**。

### 5.2 单主多从 + 调度表（Schedule Table）

LIN 是**主节点（Master）独裁**的总线：

```
主节点按"调度表"定时发帧头（Header，含 PID）
   └─ 指定的从节点（Slave）回应数据（Response）
       └─ 主节点收集 → 形成完整帧
```

- 从节点**不能主动发言**，只能被点名才答（和 CAN 的"自由竞争"相反）；
- 调度表决定"每秒点谁、点几次"，保证实时性可预测；
- 一帧最多 8 字节，速率 1K~20K bps。

### 5.3 LIN 与 CAN 的分工场景

| 维度 | CAN | LIN |
|---|---|---|
| 拓扑 | 多主竞争 | 单主多从 |
| 速率 | 125K~1M（FD 更高） | ≤20K |
| 成本 | 高 | 低（单线、简单） |
| 典型件 | 发动机、制动、网关 | 车窗、雨刷、座椅、灯光、空调面板 |

> 车机视角：LIN 上的件（如空调面板按键）通常由一个**LIN 主节点（可能是车身控制器 BCM 或车机 MCU）**收齐，再经 CAN/以太网汇总上送。车机一般不直接碰 LIN 原始帧。

## 六、车载以太网与 SOME/IP

### 6.1 为什么以太网上车

CAN 再快也才几 Mbps，扛不住 **ADAS 传感器数据流、高清影音、大块诊断/刷写数据**。车载以太网用**单对双绞线（T1）+ 交换机**提供 100M~1G 带宽、确定性低延迟。

| 标准 | 速率 | 线缆 |
|---|---|---|
| **100BASE-T1** | 100 Mbps | 单对双绞线 |
| **1000BASE-T1** | 1 Gbps | 单对双绞线（更高速率需更好线缆） |

### 6.2 SOME/IP 是什么

**SOME/IP（Scalable service-Oriented MiddlewarE over IP）** 是汽车专用的**面向服务中间件**，跑在 UDP/TCP 上。它把通信建模成"服务（Service）/ 方法（Method）/ 事件（Event）"：

```
服务 Service    ：一个可调用的能力集合（如"车门服务"）
方法 Method     ：主动调用、有请求有响应（如"锁门()"）
事件 Event      ：服务端主动推送（如"车速变化"→ 订阅者收到）
字段 Field      ：可读/可写/可订阅的状态（如"当前油量"）
```

### 6.3 SOME/IP 消息结构与序列化

一个 SOME/IP 报文大致由"协议头 + 序列化负载"组成：

```
[SOME/IP Header]
  Message ID (Service ID + Method/Event ID)
  Length / Request ID
  Protocol Version / Interface Version
  Message Type (REQUEST / RESPONSE / NOTIFICATION / ERROR)
  Return Code
[Payload]  ← 按 SOME/IP 序列化规则（大端、对齐、数组/字符串编码…）
```

> 序列化细节（struct/array/string 如何编码）由 SOME/IP 规范定义，vendor 通常用代码生成器从 **fidl / ARXML（AUTOSAR 描述文件）** 生成。Android 侧若用官方支持，会由框架/原生库处理序列化，应用不直接拼字节。

### 6.6 一次 SOME/IP 发布/订阅的时序（实例）

以"车门服务推送锁车状态"为例：

```
[服务端 ECU]                            [车机客户端]
  启动 → SD OfferService(车门服务) ──组播──▶ 收到 Offer
                                        Subscribe(锁车事件) ─▶
  <── 确认订阅 ──
  门锁变化 → 发 NOTIFICATION(锁车事件=已锁) ─▶ 客户端收到推送 → 更新 UI
  下线 → SD StopOfferService ──组播──▶ 客户端感知断连 → 标记服务不可用
```

| 消息类型 | 含义 | 类比 |
|---|---|---|
| REQUEST / RESPONSE | 方法调用、有去有回 | 函数调用 |
| NOTIFICATION | 服务端主动推送 | 事件回调 |
| ERROR | 调用失败 | 异常返回 |

> 与 VHAL 的 `subscribe` 异曲同工：车机订阅某服务/属性，底层状态一变就推上来（衔接《03 VHAL》subscribe 机制）。区别是 SOME/IP 跑在以太网、动态发现；VHAL 跑在 Binder、配置静态声明。

### 6.7 SOME/IP 与 DoIP 不要在车上搞混

| 维度 | SOME/IP | DoIP |
|---|---|---|
| 用途 | 车内服务通信（方法/事件/字段） | 诊断报文承载（UDS over IP） |
| 传输 | UDP（事件）/ TCP（方法） | TCP 13400 / UDP |
| 发现 | SOME/IP-SD | 借助 DoIP 车辆/实体发现 |
| 车机用法 | 消费车辆能力（如座舱服务） | 诊断仪/售后刷写与读码 |

### 6.4 SOME/IP-SD（Service Discovery，服务发现）

服务不是写死 IP 的，而是**动态发现**：

```
服务端周期广播"我提供 XX 服务"（SD Offer）
客户端收到后订阅 → 后续收到该服务的 Event 通知
服务下线 → SD StopOffer → 客户端感知断连
```

这就是"面向服务"的精髓：**车机不用知道某个功能在哪个 ECU、什么地址，只要订阅服务即可**。

### 6.5 Android 官方对 SOME/IP 的支持

- **Android 13（API 33）** 起，AAOS 在 `packages/services/Car` 等体系中引入对 **SOME/IP 相关的官方集成能力**（作为车云/车内服务通信的一环）。
- 在此之前，厂商多在 **vendor 原生服务**里自己集成 SOME/IP 协议栈（如 vsomeip 一类实现），再抽象给上层。
- 注意版本差异：**13 之前靠厂商自研，13+ 才开始有框架层面的官方支持**——不要假设老版本有原生 SOME/IP API。

## 七、Android 侧接入三种做法（对照表）

车机要把总线信号变成 App 能用的东西，有三条路。选哪条取决于"信号的抽象层级"和"谁来控制"。

### 7.1 三种做法对照

| 做法 | 怎么做 | 代价 | 适用场景 |
|---|---|---|---|
| **A. 写进 VHAL（成车辆属性）** | vendor VHAL 里订阅 CAN/SOME/IP，映射成 `VehicleProperty` | 受 VHAL 属性模型约束、需定义 propertyId | 标准化车辆状态（车速、门窗、HVAC） |
| **B. 独立 native service 暴露 AIDL** | vendor 原生服务直接收总线、经 AIDL 给 Framework/App | 要自己管 AIDL 接口、权限、版本 | 厂商私有能力（不进标准 VHAL 的部分） |
| **C. 独立 HAL（AIDL/HIDL）** | 抽成正式 HAL 接口（类似其他硬件 HAL） | HAL 接口维护成本最高、需版本协商 | 需要被多个 Framework 模块复用、要稳定契约 |

### 7.2 怎么选（衔接 automotive 03/04/05 篇）

- **能用标准属性表达的 → 走 A（VHAL）**：继承 VHAL 的权限模型、订阅机制、CarPropertyManager API（见《03 VHAL 详解》）。最省力、最统一。
- **标准属性没覆盖、但又要在系统里稳定复用 → 走 C（独立 HAL）**：接口契约清晰、版本可控（衔接 NDK/AIDL 篇）。
- **纯厂商私有、只给自己 App/服务用 → 走 B（native service + AIDL）**：最快，但接口是你自己维护，要注意 SELinux/权限（见第 9、10 章）。

```
总线信号（CAN/LIN/以太网）
   ├─ 标准化车辆状态 ──▶ A: VHAL 属性 ──▶ CarPropertyManager
   ├─ 需稳定契约复用 ──▶ C: 独立 HAL(AIDL/HIDL) ──▶ Framework 模块
   └─ 厂商私有能力 ──▶ B: 原生服务 + AIDL ──▶ 自家 App/服务
```

> 「**Android 视角**」：选 A 能直接复用 CarService 的所有能力（权限、回调、区域）；选 B/C 要自己补权限与生命周期管理。除非标准 VHAL 真不够，否则优先 A。

## 八、从 CAN 帧到一个车辆属性：完整链路

把第 1 章拓扑图和第 7 章接入做法串成一条**可观测的链路**。以"车速"为例：

```
① CAN 控制器/ECU  ── 发动机 ECU 周期性发 0x1A0 帧（含车速编码）
       │
② 网关 Gateway   ── 把动力 CAN 的 0x1A0 路由到车机所在的子网（或直连）
       │
③ SoC 的 CAN 驱动 ── Linux kernel 收帧，交给 SocketCAN / 字符设备
       │             可观测：candump can0 能看到原始帧
④ 字符设备/SocketCAN ── 用户态可读（/dev/canX 或 PF_CAN socket）
       │
⑤ vendor 服务     ── 按 DBC 解出车速值、做单位换算、滤波
       │             可观测：vendor 服务日志 / dumpsys
⑥ VHAL 实现       ── 把车速映射为 PERF_VEHICLE_SPEED 属性并上报
       │             可观测：dumpsys car_service 看属性值
⑦ CarService      ── 管理属性、权限、订阅
       │
⑧ App             ── CarPropertyManager 注册回调，UI 刷新
```

每一步的可观测点（出问题先定位在哪一层）：

| 层 | 看什么 | 工具 |
|---|---|---|
| ①~② 物理/网关 | 总线上到底有没有这帧 | 万用表/示波器 + 同网段其他节点 |
| ③~④ 驱动/接口 | SoC 收到没 | `candump can0` 看原始帧 |
| ⑤ vendor 服务 | 解出来的值对不对 | vendor 日志 / `dumpsys` |
| ⑥~⑦ VHAL/CarService | 属性值/状态对不对 | `dumpsys car_service` |
| ⑧ App | 回调是否触发 | logcat 看 App 层 |

> 排查铁律：**从下往上逐层验证**。如果 `candump` 都看不到帧，问题在物理/网关/驱动；如果 candump 有但 App 收不到，问题在 vendor 服务以上的抽象层。

## 九、Android 上直接操作 CAN：SocketCAN、NDK、权限与 SELinux

### 9.1 SocketCAN：Linux 原生的 CAN 接口

Android（基于 Linux）自带 **SocketCAN** 子系统，把 CAN 接口当成"网络设备"暴露：

```bash
# 起一个 CAN 接口（波特率 500K）
ip link set can0 type can bitrate 500000      # 配置 can0 的位速率
ip link set can0 up                          # 拉起接口
# 之后 can0 就像一块网卡，可用 PF_CAN socket 读写

# 收发测试（需 busybox/candump 工具）
candump can0                                 # 监听 can0 上所有帧
cansend can0 123#1122334455667788            # 发一帧：ID=0x123，数据 8 字节
```

### 9.2 在 NDK 里读写 CAN

Java 层**通常不直接碰 CAN**（Android Framework 没有公开 CAN Java API），而是在 **native（NDK/C++）** 里用 SocketCAN 的 socket 接口：

```
① socket(PF_CAN, SOCK_RAW, CAN_RAW)   ← 建一个 CAN raw socket
② bind 到 "can0" 接口
③ read() 收帧 / write() 发帧          ← 帧结构用 can_frame（含 can_id + len + data）
④ 按 DBC 解析 data 字节 → 业务含义
```

> 不写死具体结构体字段名（不同内核版本 `struct can_frame` 细节略有差异）；关键是"建 PF_CAN socket → bind can0 → read/write"。

### 9.3 为什么 Java 层通常不直接碰 CAN

| 原因 | 说明 |
|---|---|
| 无公开 Java API | Android SDK 没有 CAN 类，只能走 NDK |
| 性能 | 高频 CAN 帧在 native 处理更省 |
| 关注点分离 | 原始帧应被 vendor 服务收敛成"属性/服务"，再给上层 |

所以标准做法是：**native 服务收 CAN → 抽象成 VHAL 属性/AIDL → 上层用标准 API**。App 不该直接读 CAN。

### 9.4 权限与 SELinux（指向 SELinux 篇）

直接操作 CAN 设备涉及两层管控：

- **Linux 权限**：`/dev/canX` 或 SocketCAN 需要对应 gid/权限；普通 App 拿不到。
- **SELinux**：访问 `can_socket` 类、设备节点需要 vendor 域的 allow 规则，否则 `avc: denied`。

```
进程（vendor 服务，域 type_a）
   → 需要 SELinux 允许 type_a 使用 can_socket / 读写 can_device
   → 否则 logcat 出现 "avc: denied" 且收不到帧
```

> 规则怎么补、域怎么定义，见《SELinux 篇》。总线篇只负责"该给什么权限"：让 CAN 收发进程拥有 can 相关的 SELinux 权限与设备访问权。

## 十、信号质量与安全

### 10.1 总线负载率（Bus Load）

CAN 是共享介质，**所有报文挤在同一条线上**。负载率 = 实际占用带宽 / 总线总带宽。

```
500K bps 总线，若某周期报文群占用 400K → 负载率 80%
负载率过高 → 高优先级帧延迟变大、低优先级帧可能丢 → 实时性下降
```

经验值：动力 CAN 负载率建议控制在 **70% 以下**，否则要考虑提速（上 CAN FD / 以太网）或拆分网络（见 12.1 子网隔离）。

### 10.2 错误帧与报文丢失

CAN 有完善的错误检测（CRC、位监控、ACK 缺失）。当节点反复出错，会进入**错误被动 / 总线关闭（Bus-Off）**状态，直接掉线。

| 现象 | 可能原因 |
|---|---|
| 错误帧数量飙升 | 终端电阻缺失/损坏、线缆故障、波特率不匹配、强干扰 |
| 某 ECU 总线关闭 | 该节点硬件/驱动异常，反复发错帧被踢出 |
| 偶发丢帧 | 负载率过高、仲裁一直输给高优先级帧 |

> 排查顺序：先量终端电阻（应≈60Ω，即两 120Ω 并联）→ 比对波特率 → 看 `ip -s link` 的错误计数（第 11 章） → 隔离干扰源。

### 10.3 诊断安全：Seed-Key 机制

UDS 的 `0x27 Security Access` 不是谁都能发写命令。流程是经典的 **Seed-Key（种子-密钥）**：

```
诊断仪 请求 Seed（随机种子）
  ← ECU 返回 Seed
诊断仪 用私有算法算 Key = f(Seed)
诊断仪 发送 Key
  ← ECU 校验 Key 通过 → 解锁（进入可写/编程会话）
```

> 算法 `f` 是车厂保密的（相当于"口令生成器"）。Seed-Key 的意义：**防止随便一个设备就能刷写/改写车辆参数**。逆向或绕过它是严重安全违规，本文只讲其存在与作用边界。

### 10.5 一个 Seed-Key 数值示例（仅演示逻辑，非真实算法）

```
Seed  = 0x3F 0x8A 0x11 0xC4
假设车厂算法 f: Key = (Seed 每字节循环左移 1 位) 再异或一个固定掩码 0x55
  Key[0] = rol(0x3F,1) ^ 0x55 = 0x7E ^ 0x55 = 0x2B
  Key[1] = rol(0x8A,1) ^ 0x55 = 0x15 ^ 0x55 = 0x40
  ... 算出 4 字节 Key
诊断仪发送 Key → ECU 用同一算法验证 → 通过才解锁
```

> 真实算法远比这复杂且保密；这里只为说明"Seed 是随机挑战、Key 是对它的单向派生、双方对账"的机制。任何对真实算法的逆向都属越界，**不在本文讨论范围**。

### 10.6 总线攻击面与最小权限原则

车机挂在网络上，本身就是潜在的攻击入口，设计时遵循：

| 原则 | 做法 |
|---|---|
| **最小暴露** | 车机只接信息/车身网，动力网过网关单向转发 |
| **写操作收口** | UDS 写/刷写经 vendor 服务，不暴露给应用层 |
| **默认拒绝** | SELinux + 权限默认拒，按需开（见 9.4、SELinux 篇） |
| **解锁才写** | 关键写必须过 Seed-Key，且限白名单会话 |

### 10.4 UDS 写操作的权限边界与整车安全后果

`0x2E` 写数据、`0x31` 例程、`0x34/36/37` 刷写——这些**写操作有整车安全后果**：

```
危险操作举例：
  · 改写标定参数 → 动力/制动特性改变，可能危及安全
  · 进编程会话刷 ECU → 刷错固件 = 该 ECU 变砖
  · 关闭故障码/排放限制 → 合规与法律风险
```

「**Android 视角**」车机作为网络上一个节点，**绝不能把 UDS 写能力无防护地暴露给应用层**。正确做法：写操作经 vendor 服务收口、受 SELinux + 权限 + 业务白名单控制，且关键写操作需先过 Seed-Key 解锁。这也是第 7 章"优先走 VHAL/受控 HAL"的安全理由。

## 十二、车机场景

### 12.1 整车网络拓扑划分：动力 / 车身 / 娱乐 CAN 的隔离与网关

现实车不是一根 CAN 通到底，而是**按安全等级和速率划分子网**，由**网关（Gateway）**做协议路由与隔离：

| 子网 | 典型内容 | 隔离原因 |
|---|---|---|
| **动力 CAN（Drivetrain）** | 发动机、制动、ABS、转向 | 安全关键、高实时、低延迟 |
| **车身 CAN（Comfort）** | 门窗、灯光、空调、座椅 | 舒适件，时序宽松 |
| **娱乐/信息 CAN（Infotainment）** | 车机、仪表部分信号 | 与动力隔离，防娱乐系统拖垮安全网 |
| **车载以太网** | ADAS、影音、诊断大数据 | 高带宽需求 |

网关负责"动力 CAN 的某帧 → 娱乐 CAN/以太网"的受控转发（如把车速转发给车机显示，但**绝不让车机反向写动力控制**）。

### 12.2 为什么车机只接其中几条

车机 SoC **通常只挂在信息/车身 CAN 和以太网**上，不直接连动力 CAN：

- **安全隔离**：避免娱乐系统故障/被攻破后影响制动等安全关键网络；
- **带宽与实时性**：车机跑 Android，进程调度不确定，不适合直接抢动力总线；
- **信号经网关收敛**：车机需要的车速、档位等，由网关/域控制器转发到信息网，再以属性形式给 App。

> 这也是 VHAL 存在的意义：车机拿到的永远是"经过抽象和权限控制的属性"，而不是"任意 CAN 帧任意写"。（衔接《03 VHAL 详解》）

### 12.3 ECU 刷写：Bootloader 与 UDS 刷写流程

给某个 ECU 升级固件，标准套路是 **UDS 三段式 + Bootloader 配合**：

```
① 进扩展/编程会话（0x10） + 过 Seed-Key（0x27）
② Request Download（0x34）：告诉 ECU 要写的起始地址与长度
③ Transfer Data（0x36）：分块传固件数据
④ Request Transfer Exit（0x37）：传输结束
⑤ 复位 ECU → 其 Bootloader 校验并跳转到新固件
```

- **Bootloader**：ECU 内部的一段"出厂固化"小程序，负责把收到的固件写进 Flash 并校验。刷写中掉电 = 该 ECU 可能变砖，需返厂/售后重刷。
- 车机侧若承担"刷写网关/转发"角色，要确保刷写期间**总线稳定、不掉电、不被其他报文打断**。

### 12.4 量产下线检测（EOL, End of Line）

整车下线的"终检"会：

```
① 总线全节点扫描（确认每个 ECU 在线、ID 正确）
② 读 DTC（故障码），确认无未解决故障
③ 写 VIN / 标定 / 配置（UDS 0x2E，需解锁）
④ 自检测例程（UDS 0x31），如执行器测试
```

车机作为网络节点，也要在这一步完成"能正常收发、属性映射正确"的验证。

### 12.5 车机访问总线的点火/电源门控

车机不是一上电就能随意发总线报文，尤其在车辆休眠/唤醒、点火状态切换时，总线可能处于低功耗或部分唤醒态：

| 车辆状态 | 总线状态 | 车机该怎么做 |
|---|---|---|
| 熄火常电（ACC off，12V 在） | 部分子网休眠 | 仅维持必要监听，避免发唤醒报文打扰 |
| 点火 on（IGNITION on） | 全网上线、各 ECU 广播 | 正常订阅/消费属性 |
| 升级窗口（Park + 充电） | 稳定在线 | 可做大流量操作（刷写/大同步） |
| 唤醒事件（Remote/定时） | 局部唤醒 | 按需唤醒对应子网，控制唤醒范围 |

> 设计要点：**车机发总线报文要受点火状态与电源策略门控**，避免在休眠期广播把整车从低功耗拽醒（"幽灵耗电"）。点火状态本身经 VHAL 的 `IGNITION_STATE` 属性上报（衔接 automotive 03/04 篇），总线访问逻辑应据此收敛。这与 OTA 篇第 13 章"熄火窗口升级"是同一套电源纪律。

## 十五、一图总结与关联阅读

### 15.1 一图总结（ASCII）

```
整车的"三张网"
 ├─ 动力 CAN（高实时/安全）──┐
 ├─ 车身 CAN（舒适件）──────┼─▶ 网关 Gateway（隔离+路由，绝不反向写安全网）
 ├─ 娱乐 CAN（车机所在）────┘
 └─ 车载以太网（ADAS/影音/诊断 DoIP / SOME/IP）

车机侧链路（以车速为例）：
 ECU 广播帧 → 网关转发 → SoC CAN 驱动(SocketCAN) → vendor 服务(DBC 解析)
    → VHAL 属性 或 独立 AIDL/HAL → CarService → App
    ↑ 每一步都可观测（candump / dumpsys / logcat），从下往上逐层查

记忆链：差分仲裁(ID 小赢) → 8字节帧 + ISO-TP 分包 → UDS 诊断/Seed-Key
        → 网关隔离三张网 → 车机只接信息网 → 抽象成属性才给 App
LIN=主从低速件；SOME/IP=以太网上的面向服务（13+ 官方支持）。
安全红线：写操作必须收口、受控、过解锁，绝不暴露给应用层。
```
