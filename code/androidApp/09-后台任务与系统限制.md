# 09 后台任务与系统限制：WorkManager、JobScheduler、Alarm、前台服务

> 后台任务是 Android App 最容易和系统策略冲突的地方：代码写对了，不代表一定会按时执行。还要考虑 Doze、App Standby、后台启动限制、电池优化与厂商策略。本篇站在 **App 开发者视角**，讲"怎么写、怎么被限制、怎么合规"。
>
> 分工声明：Framework 的底层机制（Doze 的 wakefulness 切换、Alarm/JobScheduler 的内核调度）在 `androidFrameworks/15_Power机制详解` 与 `androidFrameworks/16_后台任务机制详解`；前台服务的完整生命周期在 `07_Service` 篇。本篇聚焦 App 侧实战，遇到"为什么没执行"会指回对应的 Framework 章节。

## 1. 开场：后台任务的三个时代

从 Android 诞生到今天，后台任务的"自由程度"被一刀一刀砍掉。理解了这条演进线，你才不会把"老教程里的写法"照抄到新系统上翻车。

| 时代 | 代表版本 | 系统态度 | 典型后果 |
|---|---|---|---|
| ① 随意跑 | Android 1–5（约 2014 前） | 后台 Service 随便起，想跑多久跑多久 | 进程常驻、电量和内存被吃光，"流氓软件"时代 |
| ② 后台服务受限 | Android 8（O, 2017） | 禁止后台应用随意启动 Service；引入 `startForegroundService` + 短时 `startForeground` 硬约束 | `IntentService` 退场，前台服务成为"想长期干活"的刚需 |
| ③ 全面限制 | Android 12–14（2021–2023） | 后台启动 FGS 直接抛异常、**前台服务类型强制声明**、精确闹钟权限收紧、Doze/Standby 更激进 | 不按新规写的 App 在 12+ 上**启动即崩溃** |

「Android 视角」：三个时代的转折点分别是 **API 26（O）** 和 **API 31/33/34（12/13/14）**。下面凡是版本差异都标出来，照抄前先看清楚你的最低 `minSdk`。

### 1.1 "我的代码现在能跑吗"判定流程图

拿到一个后台需求，先别急着写，用下面这张图定位它该用什么机制：

```
你的需求是什么？
│
├─ 用户关屏后还必须准点响（闹钟/提醒/吃药）?
│   └─► AlarmManager (exact)  ── 但 Android 12+ 要 canScheduleExactAlarms()
│
├─ 用户能持续感知的任务（导航/录音/运动/通话）?
│   └─► Foreground Service (FGS)，且 Android 14+ 必须声明 service type
│
├─ 可延迟、但保证最终完成（上传/同步/清理/预取）?
│   └─► WorkManager（默认落 JobScheduler，最省心）
│
├─ 系统级、带复杂约束、你是系统/预装应用?
│   └─► JobScheduler 直用 / 自定义调度（见 androidFrameworks/16）
│
└─ 只在页面活着时跑的短任务?
    └─► viewModelScope / lifecycleScope，跟进程后台无关
```

### 1.2 怎么读这篇

- 想直接选方案 → 第 5 章选型决策树 + 第 12 章排查表。
- 用 WorkManager → 第 3、4 章。

## 2. 什么算"后台"：进程状态与系统限制的区别

很多 Bug 的根源是概念混淆："我的 App 在前台还是后台"和"我的 App 在 Doze 里吗""在 Standby 里吗"是**三件不同的事**。

### 2.1 进程重要级别（对开发者有用的几个）

系统按"对用户有多重要"给进程排优先级（Importance Level），越往下越容易被杀：

| 级别 | 触发条件 | 对后台任务的意义 |
|---|---|---|
| **感知型（Perceptible）** | 有前台服务在跑、或绑定到前台应用 | 系统尽量不杀；FGS 就在这级 |
| **可见型（Visible）** | 有可见 Activity（未聚焦）、或处于画中画/暂停但可见 | 比缓存进程安全，但 Doze 仍可能延迟任务 |
| **服务型（Service）** | 仅有后台 Service 在跑 | **Android 8+ 已很难维持**——后台起 Service 受限 |
| **缓存型（Cached）** | 无任何组件活跃，仅因最近用过被保留 | 随时可能被 LMK 回收，里面的手写线程/Alarm 全失 |

「Android 视角」：ActivityManager 用 `IMPORTANCE_*` 常量（如 `IMPORTANCE_FOREGROUND_SERVICE`、`IMPORTANCE_CACHED`）给每个进程打分，这套分决定了它能不能后台干活、会不会被回收。判断自己是不是"前台"可以用 `ActivityManager.getRunningAppProcesses()` 看 `importance`，但更可靠的是自己维护"有没有可见 Activity"的标志。

### 2.2 三个常被混为一谈的概念

| 概念 | 谁决定的 | 触发条件 | 限制什么 | 怎么解除/豁免 |
|---|---|---|---|---|
| **后台进程** | AMS / 进程重要性 | 没有前台 Activity / FGS | 不能随便起 Service、不能弹 Activity | 回到前台、或走通知 PendingIntent |
| **Doze（打盹）** | DeviceIdleController | 屏幕关闭 + 静止 + 灭屏一段时间（插入充电即退出） | 延迟网络、Alarm（非 exact）、Job、WakeLock | 充电、移动、白名单、`setExactAndAllowWhileIdle` |
| **App Standby（应用待机）** | AppStandbyController | 用户一段时间没与 App 交互 | 打进"待机桶"，延迟 Job/同步 | 用户打开 App、高优先级 FCM |

关键区别一句话：**后台是"你现在活不活"，Doze 是"设备现在懒不懒"，Standby 是"用户还记不记得你"**。三者可以叠满——一个后台、且设备 Doze、且待机桶为 `restricted` 的 App，任务几乎不会跑，这正是"锁屏后啥都不动"的典型现场。

## 3. WorkManager 完整实战

WorkManager 是 Google 给"可延迟但必须最终完成"任务的标准答案。**它被设计成在不同 Android 版本上自动挑最合适的后端**：API 23+ 走 JobScheduler，低版本走 AlarmManager + BroadcastReceiver（无 GMS 也能用，详见第 9.3 节）。

### 3.1 最小可用：一个一次性任务

```kotlin
// 推荐继承 CoroutineWorker，doWork 是 suspend，天然适配 Kotlin
class UploadWorker(
    appContext: Context,
    params: WorkerParameters,
    private val repository: UploadRepository,   // 通过 WorkerFactory 注入，别在 Worker 里 new 依赖
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result {
        // inputData 来自入队时 setInputData，跨进程持久化在 WM 的数据库里
        val fileId = inputData.getString("fileId") ?: return Result.failure()

        return when (repository.upload(fileId)) {
            UploadResult.Success  -> Result.success()            // 成功：出队
            UploadResult.Retryable -> Result.retry()             // 可重试：按退避策略再来
            UploadResult.Fatal     -> Result.failure()           // 致命：标记失败，不再跑
        }
        // 失败也能带输出：Result.failure(workDataOf("err" to "..."))
    }
}
```

入队并带上约束与退避：

```kotlin
val request = OneTimeWorkRequestBuilder<UploadWorker>()
    .setInputData(workDataOf("fileId" to fileId))
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)   // 有网即可（不要求非计费）
            .setRequiresBatteryNotLow(true)                  // 不在低电量时跑
            .build(),
    )
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30.seconds)  // 重试退避，见 3.4
    .build()

WorkManager.getInstance(context).enqueue(request)
```

### 3.2 周期任务与最小间隔

```kotlin
// 第二个参数就是重复间隔；注意最小值
val request = PeriodicWorkRequestBuilder<SyncWorker>(6, TimeUnit.HOURS)
    .setConstraints(Constraints(requiredNetworkType = NetworkType.CONNECTED))
    .build()
```

「Android 视角」：**周期任务的最小间隔是 15 分钟（`PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS`）**。你传更小的值会被悄悄抬到 15 分钟，不会报错但会"不准时"。它适合同步、清理、预取，**不适合准点闹钟**（详见第 4.3 节）。

### 3.3 Constraints 全集

| 约束方法 | 含义 | 备注 |
|---|---|---|
| `setRequiredNetworkType(NetworkType)` | 网络类型 | `NOT_REQUIRED` / `CONNECTED` / `UNMETERED`(仅 Wi-Fi) / `NOT_ROAMING` / `METERED` |
| `setRequiresBatteryNotLow(true)` | 非低电量 | 低电量时任务挂起 |
| `setRequiresCharging(true)` | 充电中 | 适合大体积同步 |
| `setRequiresDeviceIdle(true)` | 设备空闲 | 与 Doze 协同，适合整理类任务 |
| `setRequiresStorageNotLow(true)` | 存储空间充足 | 大文件下载/解压前必加，避免写满 |

「Android 视角」：这些约束最终翻译成 JobScheduler 的 `JobInfo` 约束位。所以**没有 GMS 的设备上 WM 照常工作**——它只是 JobScheduler 的一层封装（见第 9.3 节）。

### 3.4 重试策略：BackoffPolicy 的两个算法与时长

当 `doWork()` 返回 `Result.retry()`，WM 不会立刻重跑，而是按退避（backoff）等待：

| 算法 | 枚举 | 等待规律（base 为 setBackoffCriteria 的时长） |
|---|---|---|
| 指数退避 | `BackoffPolicy.EXPONENTIAL` | 等待 ≈ base × 2^(重试次数-1)，这是**默认** |
| 线性退避 | `BackoffPolicy.LINEAR` | 等待 ≈ base × 重试次数 |

```kotlin
// 两个硬下限：延迟不能小于 10 秒，指数退避的 base 上限很大
.setBackoffCriteria(BackoffPolicy.LINEAR, 15.seconds)   // 注意 base 不能 < 10s (MIN_BACKOFF_MILLIS)
```

`「Android 视角」`：退避时长有**最小 10 秒**（`MIN_BACKOFF_MILLIS`）限制。设更小会被抬到 10 秒。无限 `retry()` 不会永久卡住——系统会结合待机桶与执行配额最终放弃。

### 3.5 链式任务：beginWith / then

```kotlin
val clean = OneTimeWorkRequestBuilder<CleanupWorker>().build()
val compress = OneTimeWorkRequestBuilder<CompressWorker>().build()
val upload = OneTimeWorkRequestBuilder<UploadWorker>().build()

// 串行：clean → compress → upload
WorkManager.getInstance(context)
    .beginWith(clean)
    .then(compress)
    .then(upload)
    .enqueue()

// 并行汇合：A、B 都完成后再做 C
WorkManager.getInstance(context)
    .beginWith(listOf(workA, workB))
    .then(workC)
    .enqueue()
```

`beginWith` 是链头，`then` 追加后继；同层多个 request 即并行，下一层 `then` 等全部前驱完成（类似 DAG）。

### 3.6 唯一任务与 KEEP / REPLACE 语义

同名唯一任务保证"同一时刻只有一份在跑/排队"，避免重复入队（典型：同一个 fileId 别传两次）：

```kotlin
WorkManager.getInstance(context).enqueueUniqueWork(
    "upload-$fileId",                 // 唯一名
    ExistingWorkPolicy.KEEP,          // 已存在则保留旧的，丢弃新的
    request,
)
```

`ExistingWorkPolicy` 真实取值与语义：

| 策略 | 已存在同名任务时 | 典型用途 |
|---|---|---|
| `KEEP` | 保留旧任务，新请求被丢弃 | "只跑一次"去重 |
| `REPLACE` | 取消旧的，用新的替代 | 用新参数重启任务 |
| `APPEND` | 把新任务接在旧链后面 | 在已有链尾追加步骤 |
| `APPEND_OR_REPLACE` | 旧链已完成则替换，否则追加 | 容错版追加 |

`「Android 视角」`：**没有 `CANCEL` 这个策略**。要主动取消请调用 `cancelUniqueWork(name)` / `cancelAllWorkByTag(tag)` / `cancelWorkById(id)`。原文里提到的 "CANCEL 语义" 是个常见误解——取消是独立 API，不是入队策略。

### 3.7 观察结果的三种方式

```kotlin
val wm = WorkManager.getInstance(context)

// ① LiveData：UI 层观察，生命周期安全
wm.getWorkInfoByIdLiveData(workId).observe(this) { info ->
    when (info.state) {
        WorkInfo.State.SUCCEEDED -> { /* 刷新 UI */ }
        WorkInfo.State.FAILED    -> { /* 提示失败 */ }
        else -> { /* ENQUEUED / RUNNING / BLOCKED / CANCELLED */ }
    }
}

// ② ListenableFuture：在非 UI 线程/协程里拿一次性结果
lifecycleScope.launch {
    val info = wm.getWorkInfoById(workId).await()   // 需 guava / androidx concurrent 的 .await()
}

// ③ 按 tag / 唯一名批量观察
wm.getWorkInfosByTagLiveData("sync").observe(this) { list -> /* 多个任务状态 */ }
wm.getWorkInfosForUniqueWorkLiveData("upload-$fileId").observe(this) { list -> }
```

`WorkInfo.State` 共 6 态：`ENQUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`BLOCKED`(被前置链挡住)、`CANCELLED`。UI 显示进度/结果优先用 LiveData 方式；后台逻辑用 Future。

## 4. WorkManager 的可靠性与陷阱

WM 标榜"可靠"，但"可靠"≠"准点"。下面这些坑在锁屏后现场最常见。

### 4.1 Doze 里的真实执行窗口

即便约束全部满足，当设备进入 **Doze** 后，WM（底层 JobScheduler）的任务会被整批延迟到 Doze 的"维护窗口（maintenance window）"才集中跑。维护窗口在灭屏静止期间**很少且很短**。

这意味着：你在 `setRequiresDeviceIdle(true)` 之外的普通任务，在 Doze 下也可能几小时不执行。需要"关屏后尽快跑"别用 WM——改用 `setExactAndAllowWhileIdle`（第 5 章）。

### 4.2 国产 ROM 上的真实表现

华为/小米/OPPO/vivo 等的"自启动管理""省电策略"会在 WM/JobScheduler 之上**再加一层杀进程和限制后台**。结果：

- 即便你 WM 任务入队成功，进程被厂商杀掉后任务可能要等系统"兜底调度"才跑；
- 部分 ROM 对 `PeriodicWork` 的批处理更激进，间隔被拉得更长；
- 引导用户把 App 加入厂商"白名单/自启动许可"是现实解法，但每家的入口不同（第 10 章讲检测与话术）。

`「Android 视角」`：WM 解决的是"Android 标准调度"，**不解决"厂商定制层"**。车机 ROM 同理（见第 9 章）。

### 4.3 不要用它做"准点闹钟"

WM 的设计目标是"最终一致、可延迟"。任何要求"X 点 X 分必须响"的需求（闹钟、用药提醒、定时播报）都**不该用 WM**。正确做法见第 5 章的 AlarmManager exact 分支。

### 4.4 与 Foreground Service 的衔接：expedited 与长任务 setForeground

**加急任务（expedited）**——Android 12（API 31）引入，让一次性任务尽快执行、且不受某些后台限制：

```kotlin
val request = OneTimeWorkRequestBuilder<UrgentWorker>()
    .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED)  // 超配额则降级为普通
    .build()
```

`「Android 视角」`：expedited 在底层会走"加急 Job"机制；在 Android 12 之前则借前台服务提升优先级。它**只支持一次性任务**，周期任务不可用。

**长任务（>10 分钟）**——如果 `doWork` 要跑很久，必须在超时前把自己提升为前台服务，否则 Android 12+ 会强制杀掉 worker：

```kotlin
class LongWorker(ctx: Context, params: WorkerParameters) : CoroutineWorker(ctx, params) {
    override suspend fun doWork(): Result {
        setForegroundAsync(                     // 提升到前台服务，避免被 10 分钟超时杀掉
            ForegroundInfo(NOTIF_ID, createNotification()),
        )
        return doLongRunningJob()   // 真正耗时的工作
    }
}
```

`「Android 视角」`：**Android 12 起 worker 有约 10 分钟的执行上限**，超时不调用 `setForegroundAsync` 会被系统终止。这正是 WM 与"前台服务"衔接的演进点——需要长时间保活时，worker 内部自我提升为 FGS，而不是从外部直接起一个裸 Service。

## 5. 定时任务选型决策树

把第 1 章的流程图落成"选型表 + 代码骨架"，照着抄即可。

### 5.1 一句话选型表

| 需求 | 方案 | 必读限制 |
|---|---|---|
| 可延迟、保证最终完成 | **WorkManager** | 不准点；受 Doze/Standby 延迟 |
| 准点响（闹钟/提醒） | **AlarmManager (exact)** | Android 12+ 要 `canScheduleExactAlarms` |
| 用户持续感知的任务 | **Foreground Service** | Android 14+ 必填 type + 权限 |
| 系统级/复杂约束/系统应用 | **JobScheduler 直用** | 普通 App 用 WM 即可（WM 底层就是它） |
| 页面活着时的短任务 | `viewModelScope`/`lifecycleScope` | 与后台无关 |
| 服务端实时入口 | FCM/厂商推送 | 仅唤醒，执行交给 WM/FGS |

### 5.2 四个方案的代码骨架

**WorkManager（已在第 3 章详述，略）**

**AlarmManager —— 不精确 vs 精确：**

```kotlin
val am = context.getSystemService(AlarmManager::class.java)

// ① 不精确窗口：系统可批处理，省电（推荐默认）
am.setWindow(
    AlarmManager.RTC_WAKEUP,
    triggerAtMillis,
    10.minutes.inWholeMilliseconds,   // 时间窗口，非精确
    pendingIntent,
)

// ② 精确闹钟：Android 12+ 必须先确认权限
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S && !am.canScheduleExactAlarms()) {
    // 引导去设置页开启（见 5.3）；不要静默失败
    context.startActivity(
        Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM)
            .setData(Uri.parse("package:${context.packageName}"))
            .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK),
    )
} else {
    // setExactAndAllowWhileIdle：即使 Doze 也会在窗口内尽量唤醒
    am.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAtMillis, pendingIntent)
}
```

**Foreground Service（完整合规见第 6 章）**

**JobScheduler 直用（系统/预装应用更可控）：**

```kotlin
val job = JobInfo.Builder(JOB_ID, ComponentName(context, MyJobService::class.java))
    .setRequiredNetworkType(JobInfo.NETWORK_TYPE_UNMETERED)
    .setPeriodic(15 * 60 * 1000)                 // 同样有最小间隔
    .setPersisted(true)                          // 重启后保留（需声明 RECEIVE_BOOT_COMPLETED）
    .build()
context.getSystemService(JobScheduler::class.java).schedule(job)
```

### 5.3 canScheduleExactAlarms 的申请与降级

`「Android 视角」`：Android 12（API 31）把精确闹钟收编为**受控权限** `SCHEDULE_EXACT_ALARM`。它可能被用户/系统**随时回收**，所以每次用 exact 前都要 `canScheduleExactAlarms()` 判活。两种权限：

| 权限 | 引入 | 适用 | 是否需申请 |
|---|---|---|---|
| `SCHEDULE_EXACT_ALARM` | API 31 | 闹钟/日历/提醒类 App | 需 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` 引导开启；Google Play 审查用途 |
| `USE_EXACT_ALARM` | API 33 | 闹钟/计时器等**必要**场景 | 安装即授权，**不能**引导申请，滥用会被下架 |

降级策略：若拿不到 exact 权限，退化为 `setWindow` + 尽量小的窗口，并提前一点触发以容忍延迟；切勿把"准点"硬依赖在拿不到的 exact 上。

## 6. 前台服务 App 侧合规

前台服务（FGS）是"用户能感知的长期任务"的唯一正道，但**合规门槛逐版本升高**，是 12+/14 崩溃的高发区。

### 6.1 类型声明：Android 14 必填

`「Android 视角」`：Android 14（API 34）起，启动前台服务**必须**在 manifest 声明 `android:foregroundServiceType`，否则抛 `MissingForegroundServiceTypeException`；类型还要和对应权限匹配，否则 `SecurityException`。

manifest 写法：

```xml
<service
    android:name=".SyncService"
    android:exported="false"
    android:foregroundServiceType="dataSync" />   <!-- 34+ 必填；可多类型用 "|" 拼接 -->

<!-- 基础权限（任何 FGS 都要） -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<!-- 与 type 对应的细化权限（34+ 必填其一） -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />
```

### 6.2 各类型的前提权限清单

| 类型（manifest 常量） | 枚举 | 前提权限 | 备注 |
|---|---|---|---|
| `camera` | `FOREGROUND_SERVICE_TYPE_CAMERA` | `CAMERA`（+`FOREGROUND_SERVICE_CAMERA`） | 录像/扫码 |
| `microphone` | `FOREGROUND_SERVICE_TYPE_MICROPHONE` | `RECORD_AUDIO` | 录音 |
| `location` | `FOREGROUND_SERVICE_TYPE_LOCATION` | `ACCESS_FINE_LOCATION` 或 `ACCESS_COARSE_LOCATION` | 导航/轨迹 |
| `dataSync` | `FOREGROUND_SERVICE_TYPE_DATA_SYNC` | 无运行时权限（但高频启动受限制） | 上传/下载/同步 |
| `mediaPlayback` | `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` | 无 | 音乐播放 |
| `mediaProjection` | `FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION` | 无（需用户授权录屏） | 投屏/录屏 |
| `phoneCall` | `FOREGROUND_SERVICE_TYPE_PHONE_CALL` | 通话类权限 | 通话 |
| `connectedDevice` | `FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE` | 无 | 蓝牙/外设 |
| `shortService` | `FOREGROUND_SERVICE_TYPE_SHORT_SERVICE` | 无 | 极短服务，Android 14 引入，限时使用 |
| `mediaProcessing` | `FOREGROUND_SERVICE_TYPE_MEDIA_PROCESSING` | 无 | 媒体转码，API 34 |

`「Android 视角」`：每种类型还要在 manifest 加 `FOREGROUND_SERVICE_<TYPE>` 权限（API 34 新增）。`shortService` 用于"几秒内完事"的轻任务，但它**不能**长期挂着、不能调用 `startActivity`、且到时会强制停止——不要用它规避类型限制。

### 6.3 startForeground 的时限

| 版本 | 要求 | 违反后果 |
|---|---|---|
| Android 8（26） | `startForegroundService()` 后须在规定时限（约 5 秒）内调 `startForeground()` | 不调 → 系统杀进程 / ANR |
| Android 12（31） | 后台起 FGS 受第 7 章限制 | `ForegroundServiceStartNotAllowedException` |
| Android 14（34） | 类型与权限须匹配 | `MissingForegroundServiceTypeException` / `SecurityException` |

代码骨架（与 `07_Service` 篇呼应）：

```kotlin
class SyncService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // 必须在 onCreate/onStartCommand 里尽快调用，最迟别超过 5 秒
        startForeground(NOTIF_ID, buildNotification())
        doWork()
        return START_STICKY
    }
    override fun onBind(intent: Intent?): IBinder? = null
}
```

### 6.4 用户可关闭 FGS（Android 13+ Task Manager）

`「Android 视角」`：Android 13（API 33）起系统有**前台服务任务管理器（FGS Manager）**，用户在通知栏/设置里可一键停止你的前台服务。这意味着 FGS 不是"免死金牌"——用户随时能杀。设计上别把关键数据只留在内存，停止前要能干净收尾（监听 `onDestroy` 做持久化）。

## 7. 后台启动限制（Android 12+）

`「Android 视角」`：Android 12（API 31）是后台启动的**硬分水岭**——后台应用调用 `startForegroundService` / `startService` 会直接抛 `ForegroundServiceStartNotAllowedException`（它是 `RuntimeException` 子类）。

### 7.1 哪些情况被豁免（可后台启动）

| 豁免场景 | 说明 |
|---|---|
| App 在前台（有可见/聚焦 Activity） | 最常见 |
| 刚离开前台不久（短暂宽限期） | 系统给的过渡时间 |
| 由**通知的 PendingIntent** 触发 | 用户点通知 = 视为前台意图 |
| **精确闹钟（exact alarm）** 触发 | 系统代你拉起 |
| 被系统/其他前台 App **绑定**启动 | 如 Accessibility、DeviceAdmin |
| 高优先级 FCM 到达 | 特定推送类型允许拉起 |
| 用户已授予"允许后台活动"等特例 | 厂商/权限层面 |

### 7.2 判定与防御性写法

```kotlin
fun safeStartForeground(ctx: Context, intent: Intent) {
    // 1) 先看自己是否在前台：importance 低于 IMPORTANCE_VISIBLE 即视为后台
    val am = ctx.getSystemService(ActivityManager::class.java)
    val fg = am.runningAppProcesses
        ?.firstOrNull { it.processName == ctx.packageName }
        ?.importance?.let { it <= ActivityManager.RunningAppProcessInfo.IMPORTANCE_VISIBLE }
        ?: false

    try {
        if (fg) {
            ContextCompat.startForegroundService(ctx, intent)
        } else {
            // 2) 后台：不要硬起，改为发通知让用户点开（走 PendingIntent 豁免）
            notifyUserToOpen(ctx)   // 见 7.1 的"通知触发"豁免
        }
    } catch (e: ForegroundServiceStartNotAllowedException) {
        // 3) 兜底：捕获后降级为通知，不要让它 crash 整个调用链
        notifyUserToOpen(ctx)
    }
}
```

要点：**不要假定后台能起 FGS**。能走通知 PendingIntent 就走通知；必须后台起时 try/catch 并降级。

## 8. 数据同步的正确姿势

### 8.1 省电模式（Battery Saver）与网络约束组合

`「Android 视角」`：用户开**省电模式**后，系统进一步压制后台数据与 Job——即便你的 WM 约束都满足，也可能被推迟。用 `PowerManager.isPowerSaveMode` 检测并调整策略（如省电时只做关键同步）：

```kotlin
val power = context.getSystemService(PowerManager::class.java)
if (power.isPowerSaveMode) {
    // 只跑最小同步，放弃预取/大文件
}
```

约束组合建议：大文件下载 = `setRequiresStorageNotLow(true)` + `setRequiresCharging(true)` + `NetworkType.UNMETERED`；小状态同步 = `NetworkType.CONNECTED` + `setRequiresBatteryNotLow(true)`。

### 8.2 同步适配器（SyncAdapter）vs WorkManager

| 维度 | SyncAdapter | WorkManager |
|---|---|---|
| 调度方 | 系统账户框架（需抽象账户 + ContentProvider） | 自身（底层 JobScheduler） |
| 接入成本 | 高（要 Account/Authenticator/ContentProvider） | 低（一个 Worker 类） |
| 推荐度 | 旧框架，逐步被取代 | **当前官方推荐** |
| 仍适用场景 | 多账户、与系统"账户同步"深度集成 | 绝大多数业务同步 |

结论：**新代码优先 WorkManager**。SyncAdapter 仅在你已深度依赖系统账户同步体系时保留。

### 8.3 大文件与存储约束

大文件写入前务必加 `setRequiresStorageNotLow(true)`，避免写到一半把用户存储写满导致失败/变砖体验。配合 `setRequiresCharging` 既护电池又避免用户流失流量。

## 9. 车机场景（对你价值最高）

车载 ROM 是 gaojian 的主场，后台任务在车上有几条手机上没有的规矩。

### 9.1 熄火前的收尾：ACC off 窗口极短

车机由车辆电源（ACC/常电）供电，熄火/拔钥匙后留给应用的"收尾窗口"极短（秒级，具体取决于车厂配置）。**窗口内不要发起异步网络或长事务**，必须：

- 在 `onPause`/电源状态回调里**同步**把关键状态落盘（文件/数据库/SharedPreferences），不要依赖"稍后 WM 帮你传"；
- 待下次上电或 GarageMode 再补传。

`「Android 视角」`：AAOS 通过 `car-lib` 的 `CarPowerManager` 下发电源状态，`SHUTDOWN_PREPARE` 就是"快要断电、快存盘"的信号：

```kotlin
val car = Car.createCar(context)
val power = car.getCarManager(CarPowerManager::class.java) as CarPowerManager
power.setPowerStateListener({ state, _ ->
    if (state == CarPowerManager.CarPowerStateListener.SHUTDOWN_PREPARE) {
        persistCriticalStateNow()        // 同步、快；别再起协程网络
    }
}, Runnable::run)
```

（CarPowerManager API 属 car-lib，各 AAOS 版本略有差异，以你维护的 SDK 为准。）

### 9.2 GarageMode 里能做什么

`「Android 视角」`：AAOS 有 **GarageMode**——车辆熄火停放后，系统会唤醒一段维护窗口，专门给应用做下载/同步/清理等"不急但要做"的活。具体监听与入队机制见 `androidFrameworks/16_后台任务机制详解`。App 侧要点：把"大体积更新/日志上报"排到 GarageMode 而非用户驾驶时跑。

### 9.3 车机没有 Google Play Services 时 WorkManager 的行为

**好消息：WorkManager 不需要 GMS。** 老的 `GCMNetworkManager` 才依赖 Play 服务；WM 默认后端是 **JobScheduler（API 23+）**，纯 AOSP 即可用。所以在无 GMS 的车机 head unit 上，WM 照常工作——只是底层受车厂定制的 JobScheduler/Doze 策略影响（见 4.2、第 10 章）。

### 9.4 驾驶态限制（CarUxRestrictions）

`「Android 视角」`：驾驶中系统通过 `CarUxRestrictions` 限制某些 UX（弹窗、视频、复杂导航）。这会挡住你在后台"顺手弹个 Activity"的冲动——后台任务本身能跑，但**任何 UI 必须服从驾驶限制**，具体约束见 `androidApp/13`。后台逻辑与 UI 解耦：任务在后台算完，等停车或用户主动进入再展示。

### 9.5 预装应用的常驻任务合规路线

| 身份 | 后台待遇 | 建议 |
|---|---|---|
| 系统签名 / 平台签名预装 | 可加入 Doze/Standby 白名单、持特权权限、常驻更稳 | 走 `android:persistent` 或系统白名单，别滥用；仍尽量用 WM 持久化 |
| 普通（非系统）预装 | 与第三方 App 同待遇，受 12+ 限制 | 走正规 FGS/WM，别依赖常驻线程 |

`「Android 视角」`：系统签名只是"少被限制"，不是"能乱跑"。车厂预装要常驻，应优先与 Framework 团队确认白名单/签名策略（见 `androidFrameworks/15、16`），而不是在 App 里硬扛。

## 10. 电池优化白名单与厂商定制

### 10.1 REQUEST_IGNORE_BATTERY_OPTIMIZATIONS 的合规争议

`「Android 视角」`：申请加入电池优化白名单用 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + 权限 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，但**Google Play 政策严格限制**——只有闹钟、健康等真正"必须后台准时"的 App 才能用，滥用会被下架。判定自己当前状态：

```kotlin
val pm = context.getSystemService(PowerManager::class.java)
val ignored = pm.isIgnoringBatteryOptimizations(context.packageName)  // true = 已在白名单
// 引导开启（谨慎，且确保你的场景符合政策）：
context.startActivity(
    Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS)
        .setData(Uri.parse("package:${context.packageName}"))
        .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK),
)
```

### 10.2 厂商省电对 App 的影响与检测手段

国产/车机厂商常在标准 Doze 之上叠加自家省电与自启动管理。检测手段：

```kotlin
// ① 查当前待机桶：active(10) / working_set(20) / frequent(30) / rare(40) / restricted(45)
val usm = context.getSystemService(UsageStatsManager::class.java)
when (usm.appStandbyBucket) {
    UsageStatsManager.STANDBY_BUCKET_RESTRICTED -> { /* 已被打入冷宫，后台几乎不跑 */ }
    UsageStatsManager.STANDBY_BUCKET_RARE       -> { /* 很少跑 */ }
}

// ② 命令查看 Doze 白名单（见 11 章）
```

`「Android 视角」`：待机桶（`restricted` 最惨）直接决定 Job/同步频率。车厂若把你的 App 打进 `restricted`，标准 WM 也难以按时跑——要么走系统白名单（见 9.5），要么引导用户/车厂把 App 移出限制。

## 11. 调试与验证

把"锁屏后不跑"复现为可控现场，再对症下药。

```bash
# ① 强制设备进入 Doze，验证任务是否被延迟
adb shell dumpsys deviceidle force-idle
adb shell dumpsys deviceidle unforce          # 退出 Doze

# ② 把你的 App 加入/移出 Doze 白名单
adb shell dumpsys deviceidle whitelist +com.example.app
adb shell dumpsys deviceidle whitelist -com.example.app

# ③ 把 App 打进指定待机桶，复现"被限制"现场
adb shell am set-standby-bucket com.example.app restricted
adb shell am get-standby-bucket com.example.app

# ④ 看自己的 Job 为什么没跑（状态/约束/上次执行）
adb shell dumpsys jobscheduler -s com.example.app

# ⑤ 看 Alarm 与 WakeLock 现场
adb shell dumpsys alarm | grep com.example.app
```

### 11.1 WorkManager 诊断日志开关

WM 默认只打 `ERROR` 级日志，排查时几乎看不见调度细节。开启 `DEBUG`：

```kotlin
class App : Application(), Configuration.Provider {
    override fun getWorkManagerConfiguration(): Configuration =
        Configuration.Builder()
            .setMinimumLoggingLevel(Log.DEBUG)   // 开 DEBUG 看 WM 入队/调度/重试
            .build()
    // 注意：不要再用默认初始化（别在别处调 WorkManager.getInstance 触发默认初始化前应先有配置）
}
```

开启后过滤 `WM-` 标签即可看到每次 enqueue、约束检查、执行与退避的明细。

## 12. 常见坑排查表

| 现象 | 根因 | 章节 | 第一命令/检查点 |
|---|---|---|---|
| Periodic 不准时 | 最小 15 分钟 + Doze 批处理 | 3.2 / 4.1 | `dumpsys jobscheduler -s 包名` |
| exact alarm 不触发（12+） | `canScheduleExactAlarms` 被回收 | 5.2 / 5.3 | `am canScheduleExactAlarms`? → 代码里判活 |
| FGS 启动崩溃（14） | 未声明 type / 权限不匹配 | 6.1 / 6.2 | 查 manifest `foregroundServiceType` |
| FGS 启动崩溃（12+ 后台） | `ForegroundServiceStartNotAllowedException` | 7 | try/catch + 看 `importance` |
| 任务被 Doze 推迟 | 维护窗口才跑 | 4.1 | `dumpsys deviceidle force-idle` |
| 进程被杀任务丢失 | 手写 Alarm/线程未持久化 | 3 / 框架16 | 改用 WM（自带持久化 DB） |
| 白名单申请被拒（Play） | 场景不符政策 | 10.1 | `isIgnoringBatteryOptimizations` |
| 车机熄火任务没跑 | ACC off 窗口短 + 厂商杀进程 | 9.1 | 监听 `CarPowerManager.SHUTDOWN_PREPARE` 同步落盘 |
| WM 一直 ENQUEUED | 约束不满足（无网/低电） | 3.3 | 临时放宽 Constraints 验证 |
| 厂商 ROM 不跑后台 | 自启动被禁 / 桶为 restricted | 4.2 / 10.2 | `am get-standby-bucket 包名` |
| expedited 不生效 | 周期任务不支持 expedited | 4.4 | 改一次性任务 |
| worker 被 10 分钟杀 | 长任务没 `setForegroundAsync` | 4.4 | worker 内加 `setForegroundAsync` |
| 后台弹 Activity 失败 | 后台启动限制 | 7 | 改用通知 PendingIntent |
| Standby restricted 不跑 | 用户久未交互 | 2.2 / 10.2 | `am set-standby-bucket 包名 restricted` |
| 同步适配器不触发 | 账户/ContentProvider 配置错 | 8.2 | 核对 SyncAdapter 注册 |
| 推送到了但任务没跑 | 进程被杀，非高优 FCM 未拉起 | 8 / 框架 | 用 WM 兜底 + 高优 FCM |
