# 12 测试与质量保障：Android 工程的实用测试金字塔

> 测试的目标不是追求覆盖率数字，而是让核心逻辑、数据迁移、异步状态、页面交互和发布质量都"可验证、可回归、可证明"。本篇围绕"实用测试金字塔"组织，只讲 App 层你当下能落地、能救命的测试技法。
>
> 「**Android 视角**」标注的内容可跳过，不影响理解测试原理，但它在车机/ROM 工程里会反复出现。

---

## 1. 开场：测试到底在回答哪三个问题

写测试前先想清楚，每一行测试其实都在回答下面三个问题之一。把这三个问题贴在工位上，比任何覆盖率仪表盘都管用。

| # | 问题 | 它对应的测试形态 | 没答好会怎样 |
|---|---|---|---|
| Q1 | **这段代码怎么才能不被改坏？** | 单元测试（unit test） | 改一个字段、调一个函数，下游悄悄崩，CI 全绿 |
| Q2 | **改坏了，多久能被发现？** | 集成/instrumented 测试 | 破窗效应，坏代码合进主干，发布前才暴露 |
| Q3 | **怎么向自己和别人证明它"是好的"？** | 端到端 / UI / 真机验证 | 只能口头说"我本地跑过"，无法复现、无法信任 |

把 Q1~Q3 翻译成工程语言就是：**快速反馈（快）、可靠回归（稳）、可信证明（真）**。三者权重不同——绝大多数投入应该压在 Q1（又便宜又快），少量压在 Q2，极少压在 Q3（又贵又慢但不可替代）。

下面是本篇的"测试金字塔"全貌。注意它不是装饰图，后面每一章都挂靠在这几层上。

```text
                         ▲
                        / \          ← 极少数：端到端 / 真机 UI 自动化
                       /   \             （最贵、最慢、最易 flaky）
                      /  E2E \
                     /─────────\
                    /  UI 测试  \        ← 少量：Espresso / Compose UI Test
                   /─────────────\
                  /  Instrumented  \     ← 少量：androidTest（真机/模拟器跑）
                 /     集成测试      \
                /─────────────────────\
               /    JVM 单元测试 (test)   \   ← 大量：纯逻辑 / ViewModel / Repository
              /─────────────────────────────\
             /   纯函数 / UseCase / 工具 / 算法     \  ← 最多：无 Android 依赖，秒级跑完
            /───────────────────────────────────────\
```

**怎么读这张图：**

- 越往下，**数量越多、跑得越快、越便宜、越稳定**；越往上，**数量越少、越慢、越贵、越 flaky**。
- 底座（纯逻辑单测）是你每天的"安全带"：按一下就绿/红，秒级反馈。
- 中间层（instrumented）需要装 APK 到设备，验证"Android 框架行为"——比如 Room 迁移、Hilt 注入。
- 塔尖（UI/E2E）证明"用户真的能走通"，但维护成本最高，**不要为了覆盖率硬堆**。

> 关于 VM 架构层"为什么一定要测"的动机，本篇只一句话带过：ViewModel 是 UI 状态机的唯一真相源，状态错一格界面就错一片——论证请看 **05-App 架构（MVVM/MVI）篇**。本文聚焦"怎么测"，不重复"为什么测"。

## 2. 测试的分层依据：什么代码值得测

测试不是越多越好，而是**把钱花在杠杆最高的地方**。一个朴素的判断顺序：

```text
值得测的程度（高 → 低）：

  纯逻辑 / UseCase / 算法 / 校验规则   ★★★★★   ← 无依赖、纯函数，测得最值
        ↑
  ViewModel / 状态机（MVI reducer）    ★★★★     ← 业务逻辑核心，必须测
        ↑
  Repository（缓存 / 重试 / 策略）      ★★★      ← 边界行为值得测，用 fake
        ↑
  DAO / 网络序列化 / 适配器            ★★       ← 关键路径测，其余靠集成测兜底
        ↑
  UI 组件 / 布局 / 动画                ★         ← 测关键交互即可，别测像素
```

经验法则：**改一行就会让业务出错的代码，优先测；只是"把数据摆到界面上"的胶水代码，少测或不测。**

### 2.1 `test` 与 `androidTest` 两个 sourceSet 的分界

Android Gradle Plugin 把测试代码拆成两个 source set，这是初学者最容易混淆的点：

| 维度 | `src/test`（unit test，JVM） | `src/androidTest`（instrumented，设备） |
|---|---|---|
| 运行环境 | 本机 JVM（不需要 Android 设备） | 真机 / 模拟器上的 ART |
| 速度 | 秒级，可并行几千个 | 慢，装包 + 启动 Instrumentation |
| 能访问的 API | 普通 Kotlin/JVM；**Android 框架默认是桩（stub）** | 完整 Android 框架（Context、SQLite、Binder） |
| 典型用途 | 纯逻辑、ViewModel、Repository(fake)、Flow | Room 迁移、Hilt 注入、Espresso/Compose UI |
| 运行命令 | `./gradlew testDebugUnitTest` | `./gradlew connectedDebugAndroidTest` |

**关键陷阱**：在 `test`（JVM）里直接调用 `Context.getString()`、`Looper`、`Handler` 这类 Android API，默认会抛 `StubException` 或 NPE。两个常用开关（写在 module 的 `build.gradle.kts` 的 `android { testOptions { unitTests { ... } } }` 里）：

```kotlin
android {
    testOptions {
        unitTests {
            // AGP 默认 false。设为 true 后，单测里能解析 R.string / R.id 等资源，
            // 不再为找不到资源而崩溃（但仍是"合成资源"，不是真实打包资源）。
            isIncludeAndroidResources = true
            // AGP 默认 false。设为 true 后，未实现的 Android 方法返回默认值
            // （0 / false / null）而不是抛异常——能跑但可能"假绿"，慎用。
            isReturnDefaultValues = false
        }
    }
}
```

> 「**Android 视角**」：vendor/ROM 开发者习惯在源码树里直接引用 framework 内部类。App 层不一样——**你的单测只能在 JVM 跑，凡是 `android.*` 的 API 都要当"外部依赖"对待**，要么抽接口、要么用 Robolectric 影子（shadow）补一层。这也是为什么本篇反复强调"把逻辑推到纯 Kotlin 层"。

### 2.2 一条落地铁律

> **能推到 `test`（JVM）测的，绝不放到 `androidTest`（设备）测。** 设备测试 10 秒起步、还挑机器；JVM 测试 10 毫秒起步、CI 随便并行。把 Android 依赖挡在边界（Repository 接口、UseCase 入参），核心逻辑就能纯 JVM 测。

## 3. JVM 单元测试基础：JUnit、断言库怎么选

### 3.1 JUnit 4 还是 5？AGP 的尴尬现状

JUnit 5（Jupiter）在纯 Kotlin 库里是首选，但在 Android 工程里要分两层看：

| Source set | 推荐引擎 | 说明 |
|---|---|---|
| `test`（JVM 单测） | JUnit 4 **或** JUnit 5（`useJUnitPlatform()`） | AGP 默认配的是 JUnit 4（`testImplementation "junit:junit:4.13.2"`）；想用 JUnit 5 需在 `testOptions` 里开启 `unitTests.useJUnitPlatform()`，并引入 `org.junit.jupiter` 系列依赖 |
| `androidTest`（instrumented） | **只能 JUnit 4**（ runner 是 `AndroidJUnit4`） | Instrumentation 的 runner 基于 JUnit4 的 `@RunWith` 机制，JUnit 5 的 Jupiter 引擎在 `androidTest` 里跑不起来——这是框架限制，不是你配错了 |

实际建议：**App 工程统一用 JUnit 4 心智模型**，VM/Repository 单测全部 `@Test` + `AndroidJUnit4` 风格即可，避免 `test`/`androidTest` 双引擎的认知分裂。纯 Kotlin 多平台模块（`:core:model` 之类）再单独上 JUnit 5。

最小可跑模板：

```kotlin
import org.junit.Test
import org.junit.Assert.assertEquals

class PriceCalculatorTest {
    @Test
    fun `满100减20_边界值刚好100_不减`() {
        val result = calculateDiscount(100.0)
        assertEquals(100.0, result, 0.0001)
    }
}
```

### 3.2 断言库：可读性就是生产力

三个常见选项一行对比：

| 库 | 风格 | 一句话点评 |
|---|---|---|
| `kotlin.test`（`assertTrue/assertEquals`） | 过程式 | 纯 Kotlin 模块零依赖首选，但报错信息较朴素 |
| JUnit `Assert` | 过程式 | 历史包袱，消息可读性一般 |
| **Truth**（`assertThat(x).isEqualTo(y)`） | 流式 | **推荐**：失败时 diff 友好、链式可读，Google 官方维护 |

Truth 的可读性优势在集合/对象对比上最明显：

```kotlin
import com.google.common.truth.Truth.assertThat

@Test
fun `购物车去重后_只剩两个sku`() {
    val cart = listOf("A", "A", "B")
    val dedup = cart.distinct()
    // 失败时 Truth 会打印期望集合 vs 实际集合的差异，而不是一行 "expected:3 actual:2"
    assertThat(dedup).containsExactly("A", "B").inOrder()
}
```

> 要点：**`assertThat` 不是炫技，是让测试失败时你能 3 秒定位**。断言写得越"声明式"，CI 红的时候你越省命。

## 4. Mock 与 Fake 的取舍：MockK 实战

### 4.1 先定基调：mock 越多，测试越脆

一个反直觉的真相——**mock 不是越多越好**。mock 把"实现细节"钉死在测试里：你一旦重构方法名、参数、调用次数，一堆测试跟着红，但它们测的东西其实没坏。业界共识：

- **该 mock 的**：外部边界、你无法控制或很慢的东西（网络 API、系统时间、随机、硬件）。
- **该 fake 的**：你拥有、且行为稳定的内部协作对象（Repository、DAO、本地数据源）——手写一个内存实现，比 mock 一打方法更稳、更易读。

> 经验值：一个测试文件里如果 `every { ... }` 超过 5 行，多半该把它换成 fake 了。

### 4.2 MockK 完整示例

MockK 是 Kotlin 首选 mock 框架，对 `suspend`、扩展函数、object 支持都好。三个高频能力：

```kotlin
import io.mockk.*
import kotlinx.coroutines.flow.flowOf
import kotlinx.coroutines.test.runTest

@Test
fun `登录成功_上报事件带正确userId`() = runTest {
    // 1) relaxed：未 stub 的方法返回"宽松"默认值，避免为不关心的调用写 every
    val repo = mockk<LoginRepository>(relaxed = true)
    // 2) every： stub 一个 suspend 函数，返回可控结果
    every { repo.login(any(), any()) } returns flowOf(LoginResult.Success("u_123"))

    val analytics = mockk<Analytics>(relaxed = true)
    val vm = LoginViewModel(repo, analytics)

    vm.login("user", "pwd")
    runTest { /* 推进协程 */ }

    // 3) coVerify：校验 suspend 方法"被调用过"，且参数正确
    coVerify(exactly = 1) { repo.login("user", "pwd") }

    // 4) slot：捕获传给 analytics 的实际参数，再断言内容
    val slot = slot<String>()
    verify { analytics.trackEvent(event = capture(slot)) }
    assertThat(slot.captured).isEqualTo("login_success")
}
```

- `relaxed = true`：省去对"不关心的方法"逐一 stub，适合把注意力放在被测行为上。
- `coVerify` / `verify`：前者针对 `suspend`，后者针对普通函数；`exactly = 1` 防止"多调了一次"这种隐蔽 bug。
- `slot<T>()` + `capture(slot)`：当你要断言"传出去的参数长什么样"，而非"是否调用"，用它。

### 4.3 Repository Fake 标准模板

把外部依赖收敛到一个接口，然后手写一个内存 fake。这是全篇复用率最高的模板：

```kotlin
// 1) 接口——边界契约，Production 与 Test 共用
interface UserRepository {
    suspend fun getUser(id: String): User?
    suspend fun saveUser(user: User)
    fun observeUser(id: String): Flow<User>
}

// 2) Fake——手写内存实现，行为可控、零网络、零随机
class FakeUserRepository : UserRepository {
    private val users = mutableMapOf<String, User>()
    private val flows = mutableMapOf<String, MutableSharedFlow<User>>()

    override suspend fun getUser(id: String): User? = users[id]

    override suspend fun saveUser(user: User) {
        users[user.id] = user
        flows.getOrPut(user.id) { MutableSharedFlow() }.emit(user)
    }

    override fun observeUser(id: String): Flow<User> =
        flows.getOrPut(id) { MutableSharedFlow() }
            .onStart { users[id]?.let { emit(it) } }  // 订阅即回放当前值
}

// 3) 测试里直接用 fake，而非 mock 一打 DAO/API 方法
class ProfileViewModelTest {
    private val repo = FakeUserRepository()
    private lateinit var vm: ProfileViewModel

    @Test
    fun `保存用户后_界面状态显示新名字`() = runTest {
        vm = ProfileViewModel(repo)
        repo.saveUser(User("1", "Ada"))
        // ...断言 uiState
    }
}
```

> Fake 的"标准"体现在三点：**状态可注入（你先塞数据）、行为确定性（无真实 IO）、接口一致（实现同一个契约）**。把它当生产代码一样写测试，它会是你最可靠的回归基石。

## 5. 协程与 Flow 测试：虚拟时间是救命稻草

异步是 App bug 的重灾区，也是测试最容易"假绿"的地方。Kotlin 协程给了专属测试工具，**核心是一个虚拟时钟**。

### 5.1 `runTest` 的虚拟时间语义

`runTest { ... }`（来自 `kotlinx-coroutines-test`）会启动一个 `TestDispatcher`，它带**虚拟时间**：

- 函数里的 `delay(1000)` **不会真等 1 秒**，虚拟时钟直接推进到该点；
- 所有在该 dispatcher 上排队的协程，用 `advanceUntilIdle()` 一次性跑到空闲，或 `advanceTimeBy(500)` 精确推进 500ms；
- 这让你的"延迟逻辑"测试从"秒级"变成"瞬时"，CI 里不再因真实等待而超时。

```kotlin
import kotlinx.coroutines.test.runTest
import kotlinx.coroutines.delay
import kotlinx.coroutines.test.advanceUntilIdle
import kotlinx.coroutines.test.advanceTimeBy

@Test
fun `倒计时_推进时间后_剩余归零`() = runTest {
    var remaining = 3
    launch {                       // 跑在 TestDispatcher 上
        repeat(3) { delay(1000); remaining-- }
    }
    advanceTimeBy(1000)            // 虚拟推进 1 秒，不真等
    assertThat(remaining).isEqualTo(2)
    advanceUntilIdle()             // 把剩余 2 秒也推完
    assertThat(remaining).isEqualTo(0)
}
```

> 「**Android 视角**」：虚拟时间只在 `TestDispatcher` 内有效。一旦你的协程落到了**真实的 `Dispatchers.IO` / `Dispatchers.Default`**，虚拟时钟就管不到它——这通常是"测试卡死"的根源（见第 12 章排查表）。

### 5.2 为什么必须在测试里换掉 `Dispatchers.Main`

生产代码里 `viewModelScope`、UI 回调默认跑在 `Dispatchers.Main` 上，而 **`Main` 在 JVM 单测环境里根本不存在**（它依赖 Android 主线程的 Looper）。不换，直接抛 `IllegalStateException: Dispatchers.Main not initialized`。标准做法是用 `Dispatchers.setMain` 注入一个测试调度器，并在结束时 reset：

```kotlin
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.test.*
import org.junit.rules.TestWatcher
import org.junit.runner.Description

// 复用率极高的规则：每个 VM 测试类 @get:Rule 挂上即可
class MainDispatcherRule(
    private val dispatcher: TestDispatcher = StandardTestDispatcher(),
) : TestWatcher() {
    override fun starting(description: Description) {
        Dispatchers.setMain(dispatcher)   // 把 Main 换成可控的测试调度器
    }
    override fun finished(description: Description) {
        Dispatchers.resetMain()           // 必须 reset，否则污染后续测试
    }
}
```

> 版本差异：旧写法用 `UnconfinedTestDispatcher`（一 launch 就立即跑）；新版推荐 `StandardTestDispatcher`（launch 后需 `advanceUntilIdle()` 才执行）。**统一用 `Standard` + 手动推进**，测试更可预测——这也是 AGP 8.x 配套协程库（1.6+）的默认心智。

### 5.3 用 Turbine 测 Flow 的"状态序列"

`StateFlow` / `SharedFlow` 测的是**一串值随时间的变化**，不是单个终值。手写 `toList()` 收集容易漏掉"取消时机"，社区首选 **Turbine**：

```kotlin
import app.cash.turbine.test

@Test
fun `observeUser_刷新后_依次发射old和new`() = runTest {
    repository.observeUser("1").test {        // 开启收集
        assertThat(awaitItem()).isEqualTo(User("1", "old"))  // 订阅初值
        repository.refreshUser("1")            // 触发变更
        assertThat(awaitItem()).isEqualTo(User("1", "new"))  // 新值
        cancelAndIgnoreRemainingEvents()       // 必须取消，否则 test{} 永远挂起
    }
}
```

要点：**每个 `awaitItem()` 对应 Flow 的一次发射，顺序即断言顺序**；忘记 `cancelAndIgnoreRemainingEvents()` 会让测试挂起直到超时——这是 Turbine 最常见的"误用红"。

## 6. ViewModel 测试实战：测"状态序列"，不是"方法调用"

VM 是 UI 的状态机。测 VM 的正确姿势是：**给定一串 Action，断言它吐出的一串 State 快照**——就像给状态机喂输入、比对输出，而不是去 verify "它调了哪个方法"。

### 6.1 完整示例：Action → 期望 State 序列

```kotlin
class LoginViewModelTest {
    @get:Rule val mainDispatcherRule = MainDispatcherRule()   // 第 5.2 节的规则

    private val repo = FakeLoginRepository(result = LoginResult.Success("u1"))
    private lateinit var vm: LoginViewModel

    @Test
    fun `输入账号密码登录_状态序列为 loading然后success`() = runTest {
        vm = LoginViewModel(repo)

        vm.uiState.test {                       // 收集 StateFlow
            assertThat(awaitItem()).isEqualTo(LoginUiState())   // 初始空闲态

            vm.onAction(LoginAction.Submit("user", "pwd"))
            assertThat(awaitItem().loading).isTrue()            // 进入 loading
            val done = awaitItem()                              // 结算态
            assertThat(done.loading).isFalse()
            assertThat(done.user).isEqualTo("u1")
            cancelAndIgnoreRemainingEvents()
        }
    }

    // SavedStateHandle 可在构造时传入，验证"进程重建后状态恢复"
    @Test
    fun `重建后_从SavedState恢复已填账号`() {
        val saved = SavedStateHandle(mapOf("account" to "user"))
        vm = LoginViewModel(repo, saved)
        assertThat(vm.uiState.value.account).isEqualTo("user")
    }
}
```

### 6.2 一次性事件（Channel / SharedFlow）怎么测

"导航跳转、弹 Toast"这类**只消费一次**的事件，生产里常用 `Channel` 或 `replay=0` 的 `SharedFlow`。测它时不要当 StateFlow 去比快照，而是断言"事件被发出来过"：

```kotlin
@Test
fun `登录成功_发出一次导航事件`() = runTest {
    vm = LoginViewModel(repo)
    val events = mutableListOf<LoginEvent>()

    val job = launch { vm.events.collect { events.add(it) } }  // 订阅一次性事件流
    vm.onAction(LoginAction.Submit("user", "pwd"))
    advanceUntilIdle()

    assertThat(events).containsExactly(LoginEvent.NavigateHome)
    job.cancel()
}
```

> 口诀：**State 用 Turbine 比序列，Event 用 collect 比是否发出过**。把两者混测，是 VM 测试 flaky 的常见原因。

## 7. Room / 数据库测试：迁移失败＝用户开不了 App

本地数据库是"改坏了用户直接感知"的高危区。Room 测试必须落在 `androidTest`（真机/模拟器有真实 SQLite），JVM 单测跑不了真实 DB。

### 7.1 in-memory 数据库的 androidTest 模板

```kotlin
@RunWith(AndroidJUnit4::class)
class UserDaoTest {
    @get:Rule val instantTaskExecutor = InstantTaskExecutorRule()  // 让 LiveData/架构组件同步执行

    private lateinit var db: AppDatabase
    private lateinit var dao: UserDao

    @Before fun setup() {
        // in-memory 数据库：进程退出即销毁，快且隔离；注意 allowMainThreadQueries 仅测试用
        db = Room.inMemoryDatabaseBuilder(
            ApplicationProvider.getApplicationContext(), AppDatabase::class.java
        ).allowMainThreadQueries().build()
        dao = db.userDao()
    }
    @After fun teardown() = db.close()

    @Test fun `插入用户_按id能查回`() = runTest {
        dao.insert(User("1", "Ada"))
        assertThat(dao.get("1")?.name).isEqualTo("Ada")
    }
}
```

### 7.2 迁移测试（MigrationTestHelper）

**迁移测试是 Room 里最不能省的一项**——线上 schema 升级写错，用户升级后可能直接闪退打不开。用 `MigrationTestHelper` 在旧版本 db 上跑迁移并校验：

```kotlin
@RunWith(AndroidJUnit4::class)
class MigrationTest {
    private val TEST_DB = "migration-test"

    @get:Rule val helper = MigrationTestHelper(
        InstrumentationRegistry.getInstrumentation(),
        AppDatabase::class.java,
    )

    @Test fun migrate1To2() {
        // 用旧版本号建库（此时还没应用新迁移）
        helper.createDatabase(TEST_DB, 1).apply { close() }
        // 升到 2，并校验 schema 与字段一致；不一致直接抛异常 → 测试红
        helper.runMigrationsAndValidate(TEST_DB, 2, true, MIGRATION_1_2)
    }
}
```

### 7.3 schema 导出配置（迁移测试的前提）

迁移测试依赖 Room 导出的真实 schema JSON。在 module 的 `build.gradle.kts` 里配置导出目录：

```kotlin
android {
    defaultConfig {
        // Room 会把每个版本的 schema 导出到该目录，MigrationTestHelper 靠它比对
        kapt { arguments { arg("room.schemaLocation", "$projectDir/schemas") } }
        // 若用 KSP：ksp { arg("room.schemaLocation", ...) }
    }
}
```

> 版本差异：老项目用 `kapt`，新项目（AGP 8.x + KSP）用 `ksp` 配置项；**schema 目录必须进版本控制**，否则别人/CI 跑不了迁移测试。

## 8. Instrumented 测试：Hilt 注入的测试入口

当 Production 用 Hilt 做依赖注入，测试也得走同一套注入入口，否则 `androidTest` 里 `@Inject` 的对象全是 null。

### 8.1 自定义 Hilt TestRunner（完整模板）

```kotlin
// 自定义 runner，让 Instrumentation 启动时先初始化 Hilt 组件树
class HiltTestRunner : AndroidJUnitRunner() {
    override fun newApplication(
        cl: ClassLoader?, className: String?, context: Context?
    ) = Application(cl, className, context).apply {
        // 用 Hilt 的 Application 包装，注入才能生效
    }
}

// 测试的 Application 必须挂 @HiltAndroidApp
@HiltAndroidApp
class HiltTestApplication : Application()
```

在 `build.gradle.kts` 指定 runner：

```kotlin
android {
    defaultConfig {
        testInstrumentationRunner = "com.example.HiltTestRunner"
    }
}
```

### 8.2 `HiltAndroidRule` 与 `@BindValue` 替换依赖

```kotlin
@HiltAndroidTest
@RunWith(AndroidJUnit4::class)
class LoginFragmentTest {

```

> 精髓：**Production 用真实现、测试用 `@BindValue` 换 fake**，同一套注入图、零反射黑魔法，测试既真实又可 deterministic 控制。

## 9. UI 测试：Espresso、Compose Test 与车机视角

### 9.1 Espresso：matcher + Idling 资源

Espresso 的范式是 `onView(matcher).perform(action).check(assertion)`：

```kotlin
@Test fun openDetail() {
    onView(withId(R.id.recyclerView))
        .perform(RecyclerViewActions.actionOnItemAtPosition<UserViewHolder>(0, click()))
    onView(withText("Detail")).check(matches(isDisplayed()))
}
```

**异步等待的正确姿势**：Espresso 默认只在"主线程空闲"时才执行下一步。如果你的数据来自异步（Retrofit、协程），必须注册 **Idling Resource** 告诉它"我还在忙"，否则会 race。

> ❌ 反模式：`Thread.sleep(2000)`——既拖慢又不可靠（慢机器仍可能不够）。✅ 正解：用 `IdlingRegistry` 注册一个计数型 `IdlingResource`，异步开始 `+1`、结束 `-1`，Espresso 自动等它就绪。

### 9.2 Compose UI 测试：语义树（semantics）

Compose 没有 View id，全靠 **semantics（语义树）** 定位。给关键节点加 `testTag` 是最稳的方式：

```kotlin
@get:Rule val composeRule = createComposeRule()

@Test fun clickLoginShowsLoading() {
    composeRule.setContent {
        LoginScreen(state = LoginUiState(), onLogin = {})
    }
    // 方式一：按可见文字定位（适合静态文案）
    composeRule.onNodeWithText("Login").performClick()
    // 方式二：按 testTag 定位（推荐，文案变也不碎）
    composeRule.onNodeWithTag("login_button").assertExists()
}

// 生产代码给节点打标：
Modifier.testTag("login_button")   // 或 Modifier.semantics { testTagsAsResourceId = true }
```

**Espresso 还是 Compose Test？** 一句话：View 系统用 Espresso，Compose 用 `createComposeRule()`。混合工程两个都要装——它们各管各的 UI 树，不冲突。

### 9.3 车机注意事项

「**Android 视角·车机**」：车机 HMI 常**无触摸、靠旋钮/方向键焦点遍历**。UI 测试时要额外关注：

- **焦点可达性**：用 `onNode(isFocusable())` 断言关键节点能拿到焦点，模拟旋钮 `performKeyInput { pressKey(Key.DirectionDown) }` 验证遍历顺序；
- **无触摸回退**：别只测 `performClick()`，要测"无点击事件时，焦点高亮 + 确认键"这条路径；
- **大屏多窗**：分屏/多 Activity 场景下，断言要带 `hasWindowFocus()` 等上下文，避免点到别的窗口。

## 11. 质量门禁：从 lint 到 CI 的命令组

测试写完了，**门禁**决定它能不能拦住坏代码。

### 11.1 lint 的演进：`lintOptions` → `lint`

```kotlin
android {
    // 老写法（已废弃）：lintOptions { ... }
    // 新写法（AGP 7+/8 推荐）：
    lint {
        abortOnError = true        // 有 error 级问题直接让构建失败
        warningsAsErrors = false   // 是否把 warning 当 error（严格团队可开）
        checkDependencies = true   // 顺带检查依赖的 manifest/资源问题
        baseline = file("lint-baseline.xml")  // 存量问题先"冻结"，只拦新增
    }
}
```

自定义 lint 规则（检查团队的约定，如"禁止直接用 `Log.`"）属于进阶，先会用 `baseline` 把历史债隔离即可。

### 11.2 detekt / ktlint 在 CI 的组合

- **ktlint**：只管"格式"——换行、import 顺序、命名，极快，当格式化警察；
- **detekt**：管"复杂度 / 坏味道"——过长函数、圈复杂度、潜在 bug，可配规则集。

CI 里两者并列跑，互不重叠：ktlint 保证风格统一，detekt 保证代码健康。

### 11.3 测试覆盖率：JaCoCo 的 Android 现状与务实建议

JaCoCo 在 Android 上**对 `androidTest`（设备）覆盖率支持很弱**，主要能可靠统计的是 `test`（JVM 单测）。配置：

```kotlin
buildTypes {
    debug {
        enableUnitTestCoverage = true      // AGP 7+ 新开关，统计 JVM 单测覆盖
        // enableAndroidTestCoverage = true // 设备测试覆盖，配置麻烦、数据不稳，慎开
    }
}
```

> **覆盖率是指标，不是目标。** 别为了数字去补 `getters` 的测试。盯住"核心 VM / UseCase / 迁移"这几处的覆盖，比全局 80% 更有意义。

### 11.4 单测在 CI 的 gradle 命令组

```bash
# 跑全部 JVM 单测
./gradlew testDebugUnitTest

# 只跑某个类 / 某个方法（定位失败快）
./gradlew testDebugUnitTest --tests "com.example.LoginViewModelTest"
./gradlew testDebugUnitTest --tests "com.example.LoginViewModelTest.clickLoginShowsLoading"

# 分片并行（大工程提速）：把测试拆到 N 个 shard
./gradlew testDebugUnitTest -Pandroid.testInstrumentationRunnerArguments.numShards=4 \
  -Pandroid.testInstrumentationRunnerArguments.shardIndex=0
```

## 12. 常见坑排查表（现象 | 原因 | 章节 | 第一命令/检查点）

| # | 现象 | 原因 | 章节 | 第一命令 / 检查点 |
|---|---|---|---|---|
| 1 | 单测里 `Handler`/`Looper` 直接崩 | JVM 没有 Android 主线程 Looper | 2.1 | 把逻辑抽到纯 Kotlin 层；或 `isIncludeAndroidResources=true` |
| 2 | `Dispatchers.Main not initialized` | 没换 Main dispatcher | 5.2 | 给测试类挂 `MainDispatcherRule` |
| 3 | `runTest` 里真实 IO 卡死/超时 | 协程落到真实 `Dispatchers.IO` 脱离虚拟时钟 | 5.1 | 用 `withContext(Unconfined)` 或注入测试 dispatcher |
| 4 | mock 静态方法不生效 | MockK 默认不 mock 静态，需 `mockkStatic` | 4.2 | `mockkStatic(ClassName::class)` 并 `unmockkAll()` |
| 5 | `androidTest` 设备找不到 | 多台 adb 设备 / 模拟器未启动 | 2.1 | `adb devices`；`ANDROID_SERIAL` 指定目标 |
| 6 | Compose 测试节点找不到 | 节点被合并，需 `mergeDescendants` | 9.2 | `onNodeWithTag(..., useUnmergedTree = true)` |
| 7 | UI 测试偶发红（flaky） | 异步没等 Idling 资源，用 `sleep` 兜底 | 9.1 | 注册 `IdlingResource`，删掉 `Thread.sleep` |
| 8 | Room 迁移测试 schema 版本错位 | 导出 schema 未进 git / 版本号不匹配 | 7.3 | 检查 `schemas/` 目录与 `@Database(version=)` |
| 9 | Turbine 测试挂起超时 | 忘了 `cancelAndIgnoreRemainingEvents()` | 5.3 | 每个 `.test {}` 末尾补 cancel |
| 10 | Hilt 测试 `@Inject` 对象为 null | 没用 `HiltTestRunner` / 没 `@HiltAndroidTest` | 8.1 | 检查 `testInstrumentationRunner` 配置 |
| 11 | `StandardTestDispatcher` 下断言拿到旧值 | 没 `advanceUntilIdle()` 就断言 | 5.2 | launch 后显式 `advanceUntilIdle()` |
| 12 | flaky 治理靠加重试 | 掩盖根因，红的比例越来越高 | 9.1/12 | 关掉 retry，抓一次本地复现查根因 |
| 13 | 覆盖率数字高但核心逻辑没测 | 只补了 getter/简单分支 | 11.3 | 人工审 VM/UseCase 覆盖，不追全局百分比 |
| 14 | ktlint 与 detekt 互相打架 | 规则重叠 / 格式与复杂度混淆 | 11.2 | 明确分工：ktlint 管格式、detekt 管坏味道 |
| 15 | 车机 UI 测试只测了点击 | 车机无触摸，旋钮焦点路径未覆盖 | 9.3 | 断言 `isFocusable()` + 方向键 `performKeyInput` |
| 16 | instrumented 测试装不上 APK | `testRunner` 与 `applicationId` 冲突 / 签名 | 8.1 | `./gradlew connectedDebugAndroidTest -i` 看安装日志 |

## 13. 一图总结与关联阅读

### 13.1 金字塔 + "什么代码测什么" 速查

```text
测试金字塔（投入由多到少）：
  纯函数/UseCase ──▶ JVM 单测（test）        ┐
  ViewModel 状态  ──▶ JVM 单测（test）        ├─ 秒级、CI 必跑、最多
  Repository 策略 ──▶ JVM 单测 + Fake         ┘
  Room 迁移/注入   ──▶ Instrumented（androidTest）  ── 真机、关键路径
  UI 交互/视觉     ──▶ UI 测试 / 截图回归          ── 少量、易 flaky

一句话记忆链：
  "纯逻辑下钻到 JVM 秒测 → VM 比状态序列 → 真机只验迁移与注入 →
   UI 只保关键路径 → 门禁拦新增问题 → 覆盖率是指标不是目标"
```
